# Cross-Memory v1.1 — Critic Review

**Document under review:** `docs/cross-memory/v1.1-scoping.md` (872 lines, project-scoper deliverable, dated 2026-05-09).
**Reviewer mode:** Adversarial. Escalated from thorough mode after surfacing one CRITICAL and four MAJOR findings; a fifth perspective pass was added to hunt for systemic issues.
**Locked inputs not relitigated:** four user decisions (versioning at v1.1, single-PR branch, bootstrap-only init, bare invocation = usage + conditional hint) plus two closed OQs (naming = `doctor`, debug-logging = position (a)).

---

## 1. Verdict

**REJECT.**

The scoping document is structurally sound and the surface design is largely correct, but the v1.1 framing rests on a single load-bearing claim that does not hold under inspection: that `/cross-memory doctor --post-deploy --harness cursor` can behaviorally validate the seven contract-only-verified SCs from v1. It cannot. Two of those SCs (SC-1 always-on injection and SC-16 injection-block format) depend on a sentinel-bounded `[CROSS-MEMORY]` block existing in a Cursor-native injection surface — and per `adapter-cursor.md` § 6, that surface is a documented v1 no-op. The scoping doc names this in Risk-5 and §12 item 3 but treats it as a "documentation note." It is not. It invalidates the v1.1 acceptance-gate framing in §0, §1's Gap 3, §3.2 step 4 (under Cursor), §5.3's "healthy v1.1 acceptance gate pass" definition, and Decision 1 of the locked inputs.

The planner cannot pick this up as written without either (a) the user accepting that the v1.1 acceptance gate covers Cursor for SC-2/SC-3/SC-4/SC-5 only, with SC-1/SC-15/SC-16 staying contract-verified under Cursor, or (b) the Cursor `update_sentinel_block` becoming real before v1.1 ships (which Risk-5 explicitly defers).

Beyond that one critical issue: the scoping doc has four MAJOR findings around verdict semantics for `not-applicable` checks, the bare-invocation hint becoming spammy under Cursor, the missing setup preconditions for the post-deploy walk, and Cursor's slash-command invocation surface being unspecified. These are addressable by clarifying the spec — not by rewriting it — but they must be addressed before planner pickup, because each one is a question the executor will hit and have to stop to ask.

Send back to the **project-scoper**, not the planner. Three sections need rework: §1 Gap 3 framing, §4.7 Group E `sc-behavioral-walk` definition (per-harness applicability matrix), and §5.3 the v1.1 acceptance gate (precondition steps and per-harness pass criteria).

### Critical

**Critical-1 — The v1.1 acceptance gate cannot validate SC-1, SC-15, and SC-16 behaviorally under Cursor.**

- **Section:** §0 Recommendation Summary, §1 Gap 3, §3.2 step 4, §4.7 Group E (sc-behavioral-walk), §5.3 the v1.1 acceptance gate. Risk-5 acknowledges the underlying defect but does not propagate it to the gate framing.

- **Quote (Risk-5):** "Cursor adapter update_sentinel_block is a v1 no-op. ... Document in README and v1-shipped/v1.1-shipped. ... None - documentation."

The Operation Interface Table at line 19 also marks the operation as "No-op at v1".
- **Issue:** SC-1 ("User-global preference surfaces in a different project") and SC-16 ("[CROSS-MEMORY] injection block format is correct") cannot be behaviorally walked under Cursor because the injection block they verify does not exist on the Cursor side. SC-15 (<private> markup) is similarly tied to the injection surface - the redacted content is suppressed from the always-on tier output, which under Cursor is itself empty. The scoper's framing in §0 ("the seven contract-only-verified SCs from v1; the v1 verification gap closes here") is a claim the cursor walk cannot keep. Risk-5's "documentation only" remediation is insufficient - it does not patch the gate framing in §1, §3, §4, or §5.
- **Confidence:** HIGH. Verified directly against adapter-cursor.md § 6.
- **Impact:** The v1.1 PR cannot merge under the stated criterion. Either the gate framing is wrong (the gate covers four SCs under Cursor, not seven) or the gate is unachievable until Cursor's update_sentinel_block becomes real. The locked decision 1 ("the seven contract-only-verified SCs ... shift from 'post-v1 regression' to v1.1 acceptance criteria") was made on the unstated assumption that Cursor would not be a behavioral blocker. That assumption is wrong.
- **Recommendation:** Send back to project-scoper with these three concrete edits:
  1. **§1 Gap 3 rewrite:** acknowledge that under Cursor at v1, SC-1, SC-15, and SC-16 stay contract-verified because the Cursor injection surface is a documented v1 no-op. Reframe the gate as "behaviorally verified under Claude Code; contract-verified under Cursor where the surface is a v1 no-op; full behavioral parity deferred until Cursor's update_sentinel_block is implemented."
  2. **§4.7 Group E sc-behavioral-walk rewrite:** add a per-harness applicability matrix. SC-1, SC-15, SC-16 are walked under Claude Code only. SC-2, SC-3, SC-4, SC-5 are walked under both. The walk emits not-applicable (with explicit not-applicable exit-code semantics - see Major-1) for SCs whose injection surface is not real on the active harness.
  3. **§5.3 the v1.1 acceptance gate rewrite:** the "healthy gate pass" definition under Cursor accepts not-applicable for SC-1/SC-15/SC-16. Pin the user decision: this is the v1.1 release surface; full Cursor behavioral parity is a post-v1.1 work item.

### Major

**Major-1 — `not-applicable` is referenced as a verdict but not defined in §4.5 PASS/WARN/FAIL/ERROR table or in the JSON contract.**

- **Section:** §4.5 (output formats and exit codes), §4.7 Group C (sentinel-region-content-parses), Risk-5 ("doctor's sentinel-region-content-parses under cursor will return not-applicable").
- **Quote (Risk-5):** "Doctor's sentinel-region-content-parses under cursor will return not-applicable."
- **Quote (§4.5):** Exit codes table lists pass (0), warn (1), fail (2), error (3). No not-applicable row.
- **Issue:** Per Critical-1, multiple checks under Cursor will return not-applicable. This verdict is not in the spec's exit-code table, the per-section verdict aggregation rule ("overall = worst" - where does not-applicable rank?), or the JSON shape (what string lands in verdict for a not-applicable finding?). The executor will need to decide all of this - and a competent executor will pick a reasonable convention but a different one than another competent executor would. Two implementations would diverge.
- **Confidence:** HIGH.
- **Impact:** Without a not-applicable verdict, the cursor walk under Critical-1's reframing cannot return pass overall - the Group-C and Group-E checks will return fail (no markers found, content does not parse), and the overall verdict will be fail. This collapses the gate into the same failure mode as Critical-1.
- **Recommendation:** Project-scoper adds not-applicable to §4.5's exit-code table (recommend exit code 0, same as pass, since not-applicable is "this check legitimately doesn't apply on this harness"). Adds it to the JSON verdict enum. Specifies the per-section aggregation: not-applicable is treated as pass for the overall-worst calculation. Adds it to §4.7 Group C and Group E check definitions for the cursor case.

**Major-2 — Bare-invocation first-run hint becomes permanently spammy under Cursor.**

- **Section:** §4.5.2 (conditional first-run hint), OQ-C (resolution: "fire on any empty/absent sentinel block regardless of MEMORY.md state").
- **Quote (OQ-C resolution):** "Yes - fire the hint whenever the active harness's sentinel block is absent or contains only whitespace, regardless of MEMORY.md's state."
- **Issue:** Under Cursor at v1, update_sentinel_block is a no-op. Init's step 4 reports sentinel=skipped (cursor adapter no-op at v1). The sentinel block is **never populated** under Cursor. Therefore, the first-run hint predicate (sentinel block empty/absent) is **always true** under Cursor. Every bare invocation under Cursor will print "Tip: run /cross-memory init to bootstrap this project." - even immediately after init has completed successfully. The user will see the same hint forever.
- **Confidence:** HIGH. Composes Risk-5 and OQ-C-recommended.
- **Impact:** UX defect - the hint promises action ("run init") that does not change the predicate. The scoping doc nowhere acknowledges this composition. A user running Cursor for the first time will run init (per the hint), see sentinel=skipped, then see the same hint on the next bare invocation, and reasonably wonder if init failed.
- **Recommendation:** Project-scoper adds a Cursor-side branch to the hint predicate: **under harnesses where update_sentinel_block is a documented no-op**, the hint should fire only on the first condition (~/.cross-memory/ absent). Once the canonical store is provisioned, suppress the hint regardless of sentinel-block state. Pin in OQ-C resolution. Alternative resolution: change the hint text under Cursor to "Tip: run /cross-memory init to bootstrap (Cursor injection surface deferred to post-v1)" so the user understands why the situation persists.

**Major-3 — The post-deploy walkthrough in §5.3 omits the setup preconditions the gate depends on.**

- **Section:** §5.3 (the v1.1 acceptance gate).
- **Quote (§5.3 Step 1):** "In Claude Code: $ /cross-memory doctor --post-deploy --harness claude-code"
- **Quote (§5.3 Step 2):** "In Cursor (after switching harness): $ /cross-memory doctor --post-deploy --harness cursor"
- **Issue:** The walkthrough begins with the doctor invocation in each harness. But for cross-harness-roundtrip (SC-2) to find anything, the canonical store must already contain a memory written under harness A and visible from harness B. Per SKILL.md:153, "the deploy pipeline (tooling/deploy.{ps1,sh}) does NOT provision ~/.cross-memory/." So before step 1, the operator must: (a) deploy via tooling/deploy.{ps1,sh}, (b) open Claude Code on the project, (c) run /cross-memory init, (d) run /cross-memory save to land a test memory, **then** run the doctor walk. None of (a)-(d) appear in the walkthrough. §12 item 7 mentions the deploy step but not init/save. The planner picking this up will write a five-step walk; the executor running it on a clean machine will hit a cross-harness-roundtrip failure with no canonical memory to round-trip.
- **Confidence:** HIGH.
- **Impact:** The walkthrough is unrunnable as written. Either every operator improvises the setup (and produces inconsistent state), or the gate fails on first run for the wrong reason (no canonical memory) and gets blamed on the cross-harness defect detector.
- **Recommendation:** Project-scoper adds an explicit "Step 0 - Preconditions" subsection to §5.3: deploy v1+v1.1 to the test target; in Claude Code, run /cross-memory init to bootstrap; run /cross-memory save with a known memory under project:<active-slug>; verify the canonical file lands at ~/.cross-memory/projects/<slug>/<type>_<slug>.md. Then the existing steps 1 and 2 become steps 1 and 2 of the gate. Pin the precondition steps in M5.verify-doctor.3's acceptance criteria.

**Major-4 — Cursor's slash-command invocation surface is unspecified; the walkthrough assumes Claude-Code-equivalent syntax.**

- **Section:** §5.3 step 2, §3.1, §4.1.
- **Quote:** Throughout - "$ /cross-memory doctor --post-deploy --harness cursor" (treats Cursor and Claude Code surfaces as identical).
- **Issue:** Cursor does not have a 1:1 equivalent of Claude Code's /<command> invocation in every UI surface. The deploy manifest deploys to ~/.cursor/skills/ with "transform": true - but the scoping doc has no tooling/transform-cursor-cross-memory.{ps1,sh} (per v1-shipped.md deferred table item 11: "if integration testing surfaces a Cursor-specific syntax requirement"). The cross-memory skill has no SKILL.cursor.md or SKILL.cursor.additions.md while skills/ops/ and skills/ralph-loop/ both have one and a custom transform. The scoping doc's §5.3 step-2 invocation $ /cross-memory doctor --post-deploy --harness cursor is asserted, not verified. If Cursor's slash-command surface differs (different UI surface, different argument-parser, different command discovery), the gate cannot run.
- **Confidence:** MEDIUM. The user might immediately confirm "Cursor's slash-command surface is the same" and refute the finding.
- **Impact:** If true, the entire post-deploy gate under Cursor must be redesigned (or routed through a different invocation path). If false, this is a no-op and a one-paragraph clarification in §5.3 closes it.
- **Recommendation:** Project-scoper adds a paragraph in §5.3 confirming or refuting Cursor's slash-command parity with Claude Code. If parity, cite the verification (e.g., "verified manually 2026-05-09; /cross-memory <subcommand> parses identically in Cursor's composer chat"). If not parity, scope the cursor invocation explicitly (which surface, which transform). Either resolution is one paragraph, but it must be in the doc before the planner picks it up.

## 5. Assessment of the four open OQs (A-D)

### OQ-A — Build init before doctor, in parallel, or with a shared stage first?

**Scoper's recommendation:** "Build the shared parser stage and the shared check vocabulary first (M5.implement-shared), then implement init and doctor in parallel."

**Verdict: SOUND.** The shared check-name vocabulary closes the only real coupling between the two subcommands. Init's step-3 reachability check and step-4 self-check call doctor's primitives by name, so the names must be pinned before either implementation begins. After that, the two implementation chains are independent (different "## Subcommand:" sections in SKILL.md, different output contracts, different verifier walks). The 2-3h parallelization gain is real.

**One reservation:** the scoper's effort allocation gives M5.implement-shared.1 only 1.5h for "router + shared flag parsing + check-vocabulary." The check-vocabulary alone (per Risk-7's "treat the v1.1 check names as a stable contract") deserves more attention than ~30 minutes within that 1.5h. But this is a planner-stage allocation question, not an OQ-A correctness question. **Confirm OQ-A as recommended.**

### OQ-B — Confirm scope of post-deploy walk?

**Scoper's recommendation:** "Confirm full scope (seven SCs + cross-harness roundtrip)."

**Verdict: COMPROMISED BY CRITICAL-1.** The recommendation is the right intent - full behavioral coverage of all seven contract-only-verified SCs is the whole point of treating the gate as v1.1 acceptance. But under Cursor, three of those seven (SC-1, SC-15, SC-16) cannot be walked behaviorally because the Cursor injection surface is a v1 no-op (per Critical-1). So the recommendation cannot be implemented as stated.

**Reframe:** OQ-B should be re-asked as "the post-deploy walk covers seven SCs under Claude Code (full behavioral) and four SCs under Cursor (SC-2, SC-3, SC-4, SC-5 behavioral; SC-1, SC-15, SC-16 stay contract-verified pending Cursor injection surface)." The user must confirm this reframe explicitly. **OQ-B requires user re-confirmation, not just default acceptance.**

### OQ-C — Bare-invocation hint predicate when MEMORY.md exists but sentinel block is missing?

**Scoper's recommendation:** "Fire the hint whenever the active harness's sentinel block is absent or contains only whitespace, regardless of MEMORY.md's state."

**Verdict: COMPROMISED BY MAJOR-2.** The recommendation is correct for Claude Code. Under Cursor it produces a permanent hint loop because the sentinel block never gets populated (per Major-2). The OQ-C resolution must include the Cursor-side branch. **OQ-C requires user re-confirmation with the cursor-side carve-out added.**

### OQ-D — Add doctor --version flag at v1.1?

**Scoper's recommendation:** "Defer."

**Verdict: SOUND.** The deploy manifest is already the source of truth for installed version. Adding --version would duplicate that read. The 0.5h saving is real and the flag is a clean post-v1.1 add if a real diagnostic gap surfaces. **Confirm OQ-D as recommended; ride along with default.**

## 8. What's missing - gap analysis

Sections the scoping doc does not cover that the planner or executor will need:

### 8.1 Verifier acceptance criteria - what each walk *exactly* checks

§9's M5.verify-* tasks have one-sentence descriptions ("Five-step walk on a clean store: invoke doctor --pre-deploy, assert the six default checks ran, assert overall pass"). For the planner, this is just-enough. For the executor running the verifier, the assertion shape is under-specified:

- M5.verify-init.1: what does "assert sentinel block populated" mean exactly? Does it assert the byte-count is non-zero, the SHA-256 matches an expected value, or the parsed [CROSS-MEMORY] block has at least N entries?
- M5.verify-doctor.3: "assert overall pass" composes with Major-1 (what does pass mean when some checks return not-applicable?) and Critical-1 (what does pass mean under Cursor?).
- M5.verify-bare.1 step (c): "invoke under a fresh harness with the canonical store present but the sentinel block empty" - how does the verifier achieve "fresh harness"? On a single-machine setup, switching harness means closing one IDE and opening another. That's a heavyweight step for one verifier task.

**Recommendation:** The planner pins acceptance shape in each task. Not a scoper-level fix; flagged so the planner sees it.

### 8.2 Error-path coverage

The scoping doc enumerates the happy path well. Missing:

- What happens when init runs in a half-provisioned state? E.g., ~/.cross-memory/ exists but ~/.cross-memory/user-global/MEMORY.md is missing. Does step 1 detect and repair? The lazy-provisioning sequence is "idempotent" but not explicitly "self-healing." Risk-2 covers the empty-tier case but not partial corruption.
- What happens when doctor runs while a save is in-flight? Cross-memory has no concurrency model documented. Two concurrent invocations on the same store could race on the sentinel block. The scoping doc inherits v1's silent assumption that there's no concurrency. Document explicitly.
- What happens when init runs on a read-only filesystem? The lazy-provisioning sequence will fail at step 2. Init's step 1 should produce a clean error, not a stack trace.

**Recommendation:** Add a §3.7 "Init error paths" subsection enumerating the 4-5 plausible failure modes (FS read-only, partial canonical store, sentinel block locked by another process, harness target unreachable mid-run, OOM during always-on filter). One sentence per mode.

### 8.3 Migration / rollback story

v1+v1.1 ships in one PR. If the merged PR introduces a regression in production:
- Rollback path: revert the merge commit.
- Data migration: none - the canonical store layout is unchanged from v1's lazy-provisioning sequence.

This is implicit in the doc but not stated. Worth a one-line note in §0 or §13 ("rollback = revert the merge; canonical store layout is forward-compatible") to make it explicit for the planner.

### 8.4 Permission / security touchpoints

§3.6 and §4.4 say init and doctor are skill-only. No new Bash(*) permissions are needed. Verified - the skill body uses Read/Write/Glob, not Bash. The README permission note (defect #2) is unchanged.

But: doctor's stale-shipped-artifacts check globs ~/.claude/skills/cross-memory/, ~/.cursor/skills/cross-memory/, and ~/.claude/agents/cross-memory.md. Reading from ~/.cursor/ from a Claude Code session, or ~/.claude/ from a Cursor session - does the harness allow cross-harness directory reads? The scoping doc assumes yes; not verified.

**Recommendation:** Add one sentence to §4.7 Group E stale-shipped-artifacts clarifying that cross-harness reads are read-only and assumed accessible.

### 8.5 Cross-harness coverage gaps

Composes Critical-1 + Major-2 + Major-4. The scoping doc treats Cursor as a first-class behavioral target, but the underlying surface (update_sentinel_block no-op, ambiguous slash-command invocation, hint loop) means Cursor coverage at v1.1 is functionally about half of what Claude Code coverage is. The scoper does not name this gap explicitly. **It is the single biggest unstated assumption in the doc.**
