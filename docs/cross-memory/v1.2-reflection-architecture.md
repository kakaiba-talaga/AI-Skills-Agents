# Architecture Decision Document: Cross-Memory v1.2 — `reflect` Subcommand and `intent: distill`

> **Authoritative input:** `docs/cross-memory/v1.2-reflection-requirements.md` (12-item success-criteria checklist locked at Step 5.5; Q1–Q6 resolved verbatim). The locked decisions are out-of-bounds for re-litigation. This ADD resolves Open Items (a), (c), (d) from the requirements doc, designs the seven component-level surfaces named in the architect brief, and acknowledges Open Item (b) as v1.3-deferred. The v1 ADD precedent at `docs/cross-memory/architecture-decision.md` is the structural and stylistic template.

---

## Context

Cross-memory v1.2 adds proactive discovery to the existing v1 + v1.1 system. A user who has spent weeks building a project but has not stopped to save memories can run one command — `/cross-memory reflect` — and get a machine-proposed list of candidate memories distilled from artifacts they already created (git history, plan docs, handoffs, optionally session transcripts). The user reviews each candidate and decides to save, decline, edit, or ignore. The release is strictly additive over v1 + v1.1 — SC-21 is non-negotiable, the auto-injection surface is untouched, and the existing save/recall/audit subcommands keep their observable contracts.

The locked requirements doc resolves six design questions but defers four architectural decisions to this ADD: where the "What NOT to save" rule lives, what the anti-redundancy filter thresholds are, where `last_reflect_at` is stored, and where the v1.3-deferred external-trigger contract belongs in the design space. It also leaves seven component-level shapes unspecified — the subcommand router, the `intent: distill` brief, the `reflect_declined.md` ledger, the four-source input pipeline, the staleness nudge wiring, cross-harness applicability, and edge-case handling. Without this ADD, the planner would have to make those choices implicitly, the executor would bake them into code, and the result would be either a surprise to the user at acceptance time or a structural mismatch with the rest of cross-memory.

This document gives the planner crisp boundaries: the skill body owns the report loop and source ingestion; the agent owns candidate generation under `intent: distill`; the canonical store stays the only authoritative path; the staleness nudge is read-only in both `init` and `doctor`. Every architectural decision is recorded with options, recommendation, and at least one rejected alternative.

---

## Decision Drivers

The drivers below are the constraints every option is graded against. They derive from the locked requirements doc, the v1 + v1.1 contracts that v1.2 must not regress, and this repo's established conventions.

1. **SC-21 is non-negotiable.** The `cross-memory` agent's write allowlist remains exactly `~/.cross-memory/**`, sentinel-bounded `~/.claude/projects/<active-slug>/memory/MEMORY.md`, and `_tmp_*`. The new `intent: distill` cannot widen it. The new `reflect_declined.md` ledger must live within the existing allowlist.
2. **Additive only.** No changes to v1 or v1.1 success criteria. Zero regressions. The 21 SCs plus the v1.1 behavioral closures must remain green after v1.2 lands.
3. **No silent writes.** Every persisted memory either originates from explicit `save <id>` in the reflect loop or from `/cross-memory save` directly, both of which flow through Gate 3 → Gate 4 with default-N confirmation. No supersede is silent; collisions are flagged and require explicit user choice.
4. **No auto-execution.** The staleness nudge is a hint string. Neither `init` nor `doctor` invokes `reflect`. Auto-running `reflect` is forbidden.
5. **Harness portability with feature-flagged transcripts.** The human-facing surface runs under Claude Code, Cursor, and generic harnesses. Transcript ingestion (Source 1) is Claude-Code-only and opt-in by flag. Sources 3+4+5 are universal.
6. **Match existing conventions.** Subcommand routing reuses the `SKILL.md` router pattern (audit is the closest functional analog). The agent brief uses the labeled-prose format already in place for `synthesize` and `audit`. Slug derivation reuses Decision 19 from the v1 ADD.
7. **Deterministic filter.** Given identical inputs and reference sets, two consecutive `reflect` runs must produce the same candidate set (AC15). No stochastic ordering, no time-dependent randomness in the filter.
8. **Brownfield-aware.** v1.2 extends an existing skill that ships eight subcommands today (`init`, `save`, `recall`, `list`, `forget`, `search`, `audit`, `doctor`). The router, schema validator, redaction pipeline, save gates, supersede flow, and adapter precedence chain are all reused — `reflect` plugs into the existing surface rather than rewriting it.

## Existing Architecture

The relevant existing structure the planner needs in cache when reading the rest of this document:

### v1 + v1.1 surface that v1.2 plugs into

- **Subcommand router.** `skills/cross-memory/SKILL.md` parses `$ARGUMENTS`, accepts one of eight subcommands today, and dispatches to a per-subcommand handler. Unknown subcommands print a typed error and stop. The router is the single entry point — `reflect` is a new ninth subcommand registered alongside the others.
- **Save pipeline.** Save runs through four gates (Parse → Redact → Confirm → Write) with default-N confirmation at Gate 3. Supersede branches off Gate 4 when the resolved filename collides with an existing canonical entry. The reflect loop's `save <id>` action reuses this pipeline verbatim; no new write path is introduced.
- **Audit subcommand.** `audit` is the closest functional analog to `reflect`. It builds a labeled-prose brief, dispatches the `cross-memory` agent with `intent: audit`, receives a structured report, renders it to chat, and offers per-finding actions (`refresh`, `archive`, `forget`, `redact-now`, `categorize`) each gated by the standard write-path confirmation. `reflect` follows the same shape with different inputs, a different intent, and different per-candidate actions.
- **Agent contract.** `agents/cross-memory.md` declares two intents (`synthesize`, `audit`), the labeled-prose brief format, the SC-21 write allowlist with three globs, and the explicit non-triggers list. The new `intent: distill` slots in as a peer of `audit` — same brief shape, same allowlist, same labeled-prose contract.
- **`init` and `doctor` subcommands.** Both run entirely in the skill body. `init` has a five-step sequence (Provisioning → Adapter detection → Reachability probe → Always-on filter + sentinel write → Summary output). `doctor` runs read-only checks across five groups (A–E). Neither dispatches the agent today; both have a clear post-step surface where the staleness nudge plugs in.
- **Adapter precedence chain.** Five-step harness selection (CLI flag → config field → env var → manifest probe → generic fallback) determines the active harness once per subcommand. The `--harness` flag at Step 1 already supports `claude-code | cursor | generic`. `reflect` uses the same chain — no new adapter logic.
- **Canonical store layout.** `~/.cross-memory/` with `user-global/`, `projects/<slug>/`, `harnesses/<name>/`, and `archive/`. Project-scope slugs follow Decision 19 (replace `{:, \, /, space, .}` with `-`, preserve leading dashes). `~/.cross-memory/projects/<slug>/` already exists as a per-project directory — `reflect_declined.md` plugs in there.
- **Lazy provisioning.** `~/.cross-memory/` is provisioned on first save (or eagerly on first `init`). Project-scope `MEMORY.md` is created lazily on first project-scope save. `reflect_declined.md` follows the same lazy-create pattern — never created on a project that hasn't declined anything.
- **`MEMORY.md` sentinel region.** Adapter-managed `<!-- cross-memory:begin --> ... <!-- cross-memory:end -->` region inside `~/.claude/projects/<slug>/memory/MEMORY.md`. Decision 18 keeps bytes outside the markers byte-identical. v1.2 does not touch this surface — `reflect` is not an auto-injection input.

### Doc gap to close

`~/.claude/CLAUDE.md` does not currently codify a "What NOT to save in memory" rule. The rule lives implicitly in the system-prompt auto-memory specification (which is product-side, not user-editable). The reflect filter's Reference Set D needs a stable, addressable, readable home for this rule. R10 makes closing this gap a v1.2 prerequisite.

### What v1.2 explicitly does NOT touch

- The eight existing subcommand contracts (save / recall / list / forget / search / audit / init / doctor).
- The save Gate 3 → Gate 4 pipeline.
- The supersede flow under v1.1 supersede semantics.
- The auto-injection surface (always-on tier, `[CROSS-MEMORY]` block, sentinel region).
- The redaction pipeline (`redaction.md`).
- The Claude Code, Cursor, and generic adapter contracts.
- The SC-21 allowlist on the agent.

## 1. Open Item (a) — "What NOT to save in memory" Rule Location

The reflect filter's Reference Set D needs a stable, readable, addressable home for the rule. Three concrete locations are credible.

### Options

| Option | Description | Pros | Cons | Reversibility |
| :--- | :--- | :--- | :--- | :--- |
| A — Codify in `~/.claude/CLAUDE.md` | Add a "What NOT to save in memory" section under the existing Cross-Memory-related text. User-owned, harness-portable, single source of truth. The reflect filter reads this file's content as Reference Set D. | Authoritative home — `CLAUDE.md` is where standing rules already live (lane boundaries, commit conventions, naming conventions). User can edit it without touching skill code. One file to update across both the user's daily prompt and the filter. | The file is user-installed, not part of this repo's deploy pipeline — `CLAUDE.md` lives at `~/.claude/CLAUDE.md` and the project version (`/CLAUDE.md`) is separate. The filter must read from `~/.claude/CLAUDE.md` even under Cursor, where Cursor-side instruction surfaces differ. Reading a file outside the repo creates a portability footnote for non-Claude-Code harnesses. | High — moving the rule to a sub-file later is a content move, not a contract change. |
| B — Codify in `skills/cross-memory/what-not-to-save.md` | New sub-file under the skill. Skill-owned, deploys via the manifest like every other companion file (`redaction.md`, `indexing.md`). The reflect filter reads from the deployed copy at `~/.claude/skills/cross-memory/what-not-to-save.md` (or the Cursor equivalent). | Lives with the code that consumes it — same shape as `redaction.md`. Deploys uniformly across all three harnesses. Read path is parallel to how the redaction denylist is consumed today. Single update point in the repo. User edits land via PR, which is heavier but more auditable. | The rule is conceptually a user-policy thing, not a skill thing — users may want to override it per-machine without forking the skill. | C — Hybrid: `~/.claude/CLAUDE.md` authoritative + `skills/cross-memory/what-not-to-save.md` mirror | The rule lives canonically in `~/.claude/CLAUDE.md` (Option A). A short pointer file at `skills/cross-memory/what-not-to-save.md` references the canonical home and includes a fallback minimal rule set used when `~/.claude/CLAUDE.md` is absent or unreadable. The filter prefers the canonical home and falls back to the pointer. | Best of both: user owns the rule, skill has a guaranteed read path even when the canonical home is missing. Aligns with how Cross-Memory's documentation map already mirrors content (e.g., the Documentation Sync section is mirrored in `.cursor/rules/documentation-sync.mdc`). | Two files to keep in sync. Mirror drift is a real risk — see `feedback_doc_sync_mirror_drift.md` precedent. The filter's "prefer canonical / fall back to mirror" branch is one more code path to specify and test. | Medium — collapsing to one location later means removing the mirror. |

### Recommendation

**Option A** — codify the rule in `~/.claude/CLAUDE.md`.

Why this wins against the drivers: it puts the rule where standing rules already live, gives the user a single editable home, and aligns with the existing precedent that `CLAUDE.md` is the global-instructions surface (see the existing tables for naming conventions, lane boundaries, communication style). Driver 6 (match conventions) tips the balance — every other standing rule lives in `CLAUDE.md` today; bifurcating to a skill sub-file would introduce a new shape for no marginal gain.

Option B trades user-editability for deploy uniformity, but the rule is fundamentally user-policy. A user who decides "actually, I want session transcripts captured as project facts" should be able to edit `~/.claude/CLAUDE.md` without forking the skill or filing a PR.

Option C earns its keep only when read-path reliability is the bottleneck. It is not — `~/.claude/CLAUDE.md` is the user's daily prompt; if it is missing, the user has bigger problems than reflect filtering.

**Consequences:**

- A new section "What NOT to save in memory" lands in `~/.claude/CLAUDE.md` before v1.2 ships. The exact wording is a documentor task (not architect). At minimum it lists the four exclusion categories: project goals; transient session state (tool outputs, intermediate calculations); secrets and credentials; episodic conversation logs that aren't durable facts.
- The reflect filter reads `~/.claude/CLAUDE.md` and extracts the codified rule. The read is best-effort — if the file is missing or unreadable, the filter logs a structured warning and proceeds with an empty Reference Set D. The other three reference sets still apply.
- Under Cursor and generic harnesses, the same `~/.claude/CLAUDE.md` path is read (it is the global instruction file, not Claude-Code-specific). Cursor users who customize a different instruction file can override via a config field — deferred to v1.3 if it becomes necessary.
- AC12 is satisfied by the presence of the rule in `~/.claude/CLAUDE.md`. The reflect filter referencing it satisfies Reference Set D in R5.

### Out of scope

- The exact wording of the rule. That is a documentor task at execute time, informed by what the user has historically rejected via `decline` (data we won't have until v1.2 has run for a while).
- A parser for `~/.claude/CLAUDE.md` markdown. v1.2 reads the section by heading match (`## What NOT to save in memory`) and treats the body as a free-text rule corpus the agent prompts itself with. No structured parsing.

## 2. Open Item (c) — Anti-Redundancy Filter Thresholds

The filter drops candidates whose slug-overlap + tag-overlap + body-token Jaccard score exceeds a threshold against any of four reference sets. R5 leaves the thresholds explicitly unspecified at the requirements level. Defaults must be configurable.

### Calibration heuristic

The filter measures three signals between a candidate and each reference entry:

- **Slug overlap.** Normalized Levenshtein-like similarity on the candidate's proposed slug versus the reference's slug. Range 0.0 (no shared substrings beyond noise) to 1.0 (identical).
- **Tag overlap.** Jaccard similarity on the tag sets — `|A ∩ B| / |A ∪ B|`. Range 0.0 to 1.0.
- **Body-token Jaccard.** Tokenize each body to lowercased word-tokens (excluding stopwords and punctuation), take the first 200 tokens of each (bounded sample — preserves determinism on long bodies), and compute Jaccard. Range 0.0 to 1.0.

The candidate is dropped if **any one of these three signals individually crosses its threshold against any one reference entry across the four reference sets.** This is a disjunction, not a sum — `OR` of three single-signal triggers, not an additive score. The reason: a tag-overlap of 1.0 with a body-Jaccard of 0.0 (same topic, different content) is still a duplicate to surface to the user, but a body-Jaccard of 0.95 with a tag overlap of 0.0 is also a duplicate (same content, different tags). A sum-of-signals model would dilute either signal alone.

### Options for default threshold values

| Option | Slug threshold | Tag threshold | Body-Jaccard threshold | Pros | Cons | Reversibility |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| A — Conservative (drop more) | 0.7 | 0.6 | 0.5 | Aggressive de-duplication. The user sees fewer candidates per run; less list fatigue. Encourages distinct, well-framed memories — anything overlapping with existing entries gets dropped before the user sees it. | Risks dropping legitimate refinements. A candidate "Use pytest with type hints" against existing "Use pytest" would be dropped at tag=1.0 even though the refinement is the point. False negatives are silent — the user never knows what was filtered out unless they pass `--verbose`. | High — config field. |
| B — Balanced (recommended) | 0.85 | 0.8 | 0.7 | Drops obvious duplicates while letting refinements through. A 0.7 body-Jaccard means roughly 70% token overlap — that is "saying the same thing in mostly the same words" rather than "related topic." Tag threshold of 0.8 means almost-but-not-quite identical tag sets are kept (the user can decline if uninteresting). Slug threshold of 0.85 catches paraphrased names without dropping legitimate adjacent memories. | More candidates per run than Option A. Some near-duplicates still reach the report and require the user to decline them. | High — config field. |
| C — Permissive (drop less) | 0.95 | 0.95 | 0.9 | Almost everything reaches the user. Maximum recall; the filter is essentially a guardrail against verbatim duplicates only. | List fatigue is real. On a project with months of memories, even a balanced run can produce 20+ candidates; permissive defaults push that toward 50+. Encourages the user to decline reflexively, which trains them out of careful review. | High — config field. |

### Recommendation

**Option B** — balanced defaults: slug 0.85, tag 0.8, body-Jaccard 0.7.

Why this wins against the drivers: it balances driver 7 (deterministic filter — given identical inputs the same candidates drop) against G4 (anti-noise by construction) without being so aggressive that legitimate refinements are silently lost. The body-Jaccard threshold at 0.7 is the load-bearing one — empirically, two memories phrased about the same fact in mostly the same words share roughly 70–85% of the first 200 tokens (function words, technical vocabulary, structural phrasing). Below 0.7, two memories typically reflect genuinely different facts even if they share a tag set. Above 0.7, the user is almost always seeing the same content twice.

Option A is too aggressive — refinements are the most valuable kind of candidate `reflect` can surface, and dropping them silently undercuts the entire feature. Option C is the no-defaults case — the filter exists but barely fires, which means the user does the de-duplication work the filter was supposed to do.

**Consequences:**

- The `config.yaml` schema gains three new fields under a `reflect:` namespace: `slug_overlap_threshold` (default `0.85`), `tag_overlap_threshold` (default `0.8`), `body_token_jaccard_threshold` (default `0.7`). These are read by the skill before dispatching the agent and passed into the brief.
- The `intent: distill` brief includes the resolved thresholds as constraints. The agent applies the deterministic filter as a final pass before returning candidates — the agent does not invent its own thresholds, and the filter is reproducible on a different machine given the same config.
- The `--verbose` flag on `reflect` (added at v1.2) prints per-candidate filter decisions: how many references were checked, which signal tripped, what the score was. This makes false-negative analysis tractable for the user.
- A future v1.3 calibration pass against real decline-ledger data may tune these defaults. The configurability means users can override per-machine without waiting for the next release.

### Out of scope

- The exact tokenization rules for body-Jaccard. The brief specifies "lowercased word-tokens, stopword-filtered, first 200 tokens" but the stopword list and exact tokenizer choice are an executor task. Recommend reusing whatever Python's `re` module produces with `\b\w+\b` and a standard English stopword list (NLTK or a hardcoded short list).
- Calibration against a real corpus. The recommended defaults are reasoned, not measured. After v1.2 has been used for 30+ days on at least three projects, a follow-up calibration is a v1.3 task.
- A weighted or learned score model. Out of scope for v1.2 — deterministic disjunction is enough.

## 3. Open Item (d) — `last_reflect_at` Storage Location

The staleness nudge in `init` and `doctor` reads `last_reflect_at` and emits the hint when the threshold is crossed. The storage location must respect SC-21 (writes by the agent stay within the existing allowlist).

### Options

| Option | Description | Pros | Cons | Reversibility |
| :--- | :--- | :--- | :--- | :--- |
| A — Canonical store frontmatter on a dedicated `user-global` entry | A new memory at `~/.cross-memory/user-global/_meta_reflect_state.md` carries a `last_reflect_at:` frontmatter field. Updated by the skill at the end of every successful `reflect` run. | SC-21 trivially satisfied — `~/.cross-memory/**` already in the allowlist. Reuses the existing memory schema and lazy-provisioning. Discoverable via `/cross-memory list --scope user-global`. | A meta-memory is a category violation. Memories are for user-facing facts; reflect-state is plumbing. Pollutes the user-global scope with content the user did not author. Showing up in `/cross-memory list` is noise. Versioning the meta-schema (next time we need a third state field) is awkward. | Medium — would force a list-filter convention to hide meta entries. |
| B — Per-project state file under `~/.cross-memory/projects/<slug>/state.toml` (recommended) | A small TOML file at `~/.cross-memory/projects/<slug>/state.toml` carries `last_reflect_at = "<ISO-8601-UTC>"` and any future per-project state fields. Created lazily by the skill after a successful `reflect` run. | SC-21 satisfied — `~/.cross-memory/**` covers it. Per-project granularity is correct: reflect runs are per-project, so the staleness threshold is per-project too. TOML is a stable structured format that does not conflict with the memory schema. Sits next to `reflect_declined.md` in the same per-project directory — natural co-location. Easy to extend with future fields without touching memory frontmatter. | Adds a non-Markdown file format to the canonical store (TOML alongside YAML config and Markdown memories). Minor format proliferation. | High — moving to a different location is a one-time file migration. |
| C — Global `~/.cross-memory/state.toml` | A single global state file with one entry per project: `[projects.<slug>] last_reflect_at = "..."`. Updated after every `reflect` run regardless of project. | One file to inspect; trivial to enumerate "all projects I have run reflect on, when." | Read/write contention across concurrent invocations under different projects (rare but real for power users with multiple terminals). Loses the natural per-project locality — every reflect run touches a global file. Migration when a project slug changes (rename, move on disk) is more complex. | High but with the contention asterisk. |
| D — Harness config file (e.g., the existing `~/.cross-memory/config.yaml`) | Extend `config.yaml` to carry `last_reflect_at:` per-project as a nested map. | Reuses the existing config surface; one file to deploy, one schema. | `config.yaml` is configuration (user-edited, persistent, deliberate). State is automation-written (frequent, transient, agent-managed). Mixing concerns is a recipe for the user's manual edits getting clobbered by the next `reflect` write — and the schema validator's reject behavior makes a malformed merge fatal. SC-21 is fine but the concept boundary is broken. | Medium — schema reshape. |

### Recommendation

**Option B** — `~/.cross-memory/projects/<slug>/state.toml`, lazily created.

Why this wins against the drivers: per-project granularity matches the staleness model (the hint fires when *this project* has not been reflected on in N days, regardless of other projects). SC-21 is trivially satisfied because everything under `~/.cross-memory/**` is in the agent's write allowlist — though in practice the skill, not the agent, writes the state file (the agent only generates candidates; persistence happens in the skill body after the agent returns). Co-locating with `reflect_declined.md` keeps all per-project reflect state in one directory, which makes audit-by-eye and future cleanup commands trivial.

Option A pollutes the user-global memory scope with content the user did not author — that is a soft violation of the "memories are user facts" framing in the v1 ADD's Decision 17. Option C trades per-project locality for global enumeration, and the contention case is real once a user has more than one terminal open. Option D mixes config and state concerns and would risk clobbering user-edited config.

**Consequences:**

- A new file `~/.cross-memory/projects/<slug>/state.toml` is created lazily on the first successful `reflect` run for a project. Schema:
  ```toml
  schema_version = 1

  [reflect]
  last_reflect_at = "2026-05-13T14:32:01Z"
  last_reflect_candidate_count = 7
  last_reflect_run_id = "reflect-2026-05-13T14-32-01Z"
  ```
  Additional fields may be added in future versions without bumping `schema_version` (additive only). A breaking shape change bumps the version.
- The skill writes the state file at the end of every successful `reflect` run (regardless of whether the user saved zero or all candidates). The write is one of the skill's own actions, not the agent's — `state.toml` does not pass through the agent at all. The agent reads it (to surface staleness context in the brief) but never writes to it.
- `init` and `doctor` read `state.toml` for the active project to compute the staleness hint. If the file is absent or `reflect.last_reflect_at` is missing or unparseable, both subcommands treat it as "unset" — the hint MUST NOT fire (per R8 and AC8).
- The `staleness_threshold_days` config field (already present in `~/.cross-memory/config.yaml`) is reused for the `reflect` staleness window — same field, same default of 30 days for reflect (distinct from the existing 90-day default for memory `verified_at` staleness; see "Threshold field naming" below). The default is configurable.
- AC8 and AC9 are satisfied: the hint fires when `(now - last_reflect_at) > threshold` and never auto-executes.

### Threshold field naming

`config.yaml` already has `staleness_threshold_days` defaulted to `90` for memory `verified_at` staleness. The reflect staleness window is 30 days by default, which is a different threshold. The cleanest resolution is a new config field, `reflect_staleness_threshold_days`, defaulting to `30`. Adding it is additive — old configs without the field fall back to the default at read time.

### Out of scope

- TOML parser choice. The executor picks whatever is idiomatic for the implementation context. The skill ships as Markdown documentation today; the actual file-read is performed by Claude Code's harness primitives (Read tool over the file path). Parsing TOML in a Markdown skill is the executor's problem.
- Schema migration for future versions. Out of scope for v1.2 — `schema_version = 1` is the only version that exists.

## 4. Subcommand Routing — `/cross-memory reflect`

### Where it lands in `SKILL.md`

`reflect` is a new ninth subcommand registered alongside the eight existing ones. The router section at the top of `SKILL.md` (lines 4–9) gains `reflect` in the accepted-values list. A new `## Subcommand: reflect` section is added — placement should follow the existing `## Subcommand: audit` section (audit is the closest functional analog).

### Argument grammar

```
/cross-memory reflect \
  [--from-session <session-id>] \
  [--since-last-reflect] \
  [--from <path>] \
  [--scope <user-global|project:<slug>|harness:<name>>] \
  [--staleness-days <N>] \
  [--verbose]
```

Flag interactions:

- `--from-session <id>` and `--since-last-reflect` are mutually exclusive. Both invoke Source 1 (transcript ingestion). Only valid under Claude Code; under Cursor or generic, either flag fails fast with a structured error: `error: --from-session and --since-last-reflect are Claude-Code-only flags; current harness is <name>`.
- `--from <path>` (Source 5) is always available. Multiple `--from` arguments are valid and select the union of paths.
- Absent any of the above three flags, `reflect` ingests Sources 3 + 4 by default under all harnesses.
- `--scope` restricts the candidate generation scope. Defaults to `project:<active-slug>` if omitted (the natural reflect scope). `user-global` and `harness:<name>` are valid but unusual — the architect notes them as legal but expects most invocations to be project-scoped.
- `--verbose` enables per-candidate filter decisions in the output (as described under Open Item (c)).

### `--non-interactive` deferred-but-not-precluded

Per requirements R12 and Open Item (b), the non-interactive entry point is v1.3. v1.2 does not parse `--non-interactive`, but the argument grammar above is intentionally extensible — adding a `--non-interactive` flag in v1.3 does not require any restructuring of the existing flags. The flag would short-circuit the interactive loop and emit a structured JSON candidate list with the exit codes defined in Open Item (b).

### Routing flow

Per-invocation steps in the skill body:

1. Parse flags. Reject mutually-exclusive combinations and harness-mismatched flags with typed errors.
2. Run the adapter selection chain (same as every other subcommand) to determine active harness. Reject Source 1 flags here if the harness is not `claude-code`.
3. Run lazy provisioning if `~/.cross-memory/` is absent (same as save's first action today).
4. Build the four-source input set per Section 7. Construct the labeled-prose brief.
5. Dispatch the `cross-memory` agent with `intent: distill` and the brief.
6. Receive the candidate list from the agent. Render the audit-style report to chat.
7. Enter the interactive loop. Accept `save <id>` / `decline <id>` / `edit <id>` / `done`.
8. On `done`, write the updated `state.toml` (Section 3) and emit the run summary.

### Out of scope

- The exact JSON shape for `--non-interactive`. That is v1.3's design space — see Open Item (b).

## 6. `reflect_declined.md` Ledger Schema

The ledger persists per-project decline events so subsequent `reflect` runs filter out previously-declined candidates (Reference Set C).

### Location

`~/.cross-memory/projects/<slug>/reflect_declined.md`. Created lazily on first decline. Sits next to `state.toml` and the project's `MEMORY.md`.

### SC-21 compliance check

The path matches the first allowlist glob (`~/.cross-memory/**`). The agent does not write this file — the **skill** does, after the user types `decline <id>`. Verified compliant.

### Format

Markdown with structured frontmatter on a per-entry basis. The file is conceptually append-only — each decline event is a new section delimited by `---`. The schema:

```markdown
# Reflect — Declined Candidates

Per-project ledger of memory candidates the user has explicitly declined during `reflect` runs. Consulted by the anti-redundancy filter (Reference Set C). Append-only — declines are never silently removed.

---

declined_at: 2026-05-13T14:35:11Z
candidate_id: c2
proposed_name: Use SQLite for code-intel index
category: architectural-decisions
scope: project:D--Repositories-Personal-Git-AI-Skills-Agents
tags: [code-intel, storage]
body_preview: ADD §X selects SQLite over filesystem walks for query workload.
source_evidence: docs/plan/code-intel-architecture.md#L142-L160
run_id: reflect-2026-05-13T14-32-01Z

---

declined_at: 2026-05-13T14:36:02Z
candidate_id: c5
proposed_name: Always test against the v1 acceptance gate
category: workflow-patterns-from-successful-runs
scope: project:D--Repositories-Personal-Git-AI-Skills-Agents
tags: [verification]
body_preview: Every cross-memory release runs the v1 + v1.1 acceptance gate before merging.
source_evidence: docs/ops-dispatch-log-2026-05-08.md#L45-L67
run_id: reflect-2026-05-13T14-32-01Z

---
```

### Why this format

- **Markdown over JSON/TOML.** Cross-memory ships as Markdown across the board — memories, redaction, indexing, adapter contracts. The ledger should follow the same convention. A user inspecting the ledger should see content they recognize.
- **Per-entry frontmatter block instead of YAML array.** Each entry is its own bounded record. Appending is just emitting a new block and a `---` separator. No parser needs to round-trip the entire file.
- **`---` as inter-entry delimiter.** Aligns with the YAML frontmatter convention already in use across memory files. The first `---` separates the human-readable header from the first entry; subsequent `---` separates entries.

### Write semantics

- **Append-only.** Each `decline <id>` appends a new entry. No supersede on the ledger itself. Even if the user declines the same proposed-name twice across two runs, both entries are recorded. This is intentional — the ledger documents user intent over time.
- **No on-disk deduplication.** The filter's matching strategy (next section) handles the case where two declined entries reference effectively the same candidate.
- **Skill-owned write.** The skill writes the entry in its body after `decline <id>` returns from the interactive loop. The agent never touches this file at write time.

### Matching strategy (how the anti-redundancy filter reads it)

When `distill` runs, the agent reads every entry in `reflect_declined.md` and treats each entry as a reference element for the slug/tag/body-Jaccard filter (per Section 2). The same three thresholds apply. A new candidate that matches any declined entry above any threshold is dropped.

Concretely, the entries are parsed as a list of `(proposed_name, category, scope, tags, body_preview)` tuples. The filter computes the three signals between the new candidate and each tuple. If any signal crosses its threshold against any tuple, the candidate drops with the filter reason `declined-redundancy`.

### Schema versioning

The header block at the top of the file is fixed. If the schema needs to change in v1.3+, a new top-level `schema_version: 2` field appears in each entry; older entries are interpreted at `schema_version: 1` by absence. This keeps the ledger forward-compatible without a migration step.

### Out of scope

- A `reflect --rescind <candidate_id>` command to remove an entry from the ledger. v1.2 is append-only. A future version can add rescind if real demand surfaces.
- Ledger pruning by age. The file grows monotonically. If size ever becomes a problem (unlikely — entries are small), a `--prune-older-than <days>` flag is a v1.3+ addition.

## 7. Four-Source Input Pipeline Shape

The pipeline unifies four input sources into a single corpus the agent distills from. The shapes differ; the contract to the agent is uniform.

### Source 3 — git history + working-tree conventions

**Scanned by the skill before the agent dispatch.** The skill runs read-only `Bash` commands:

- `git log --pretty=format:"%H%n%an%n%ae%n%s%n%b%n---END---"` (configurable bound — default last 90 days or 200 commits, whichever is smaller). Captures commit SHA, author, subject, body.
- `git diff --stat <oldest-in-range>..HEAD` for diffstat-level signals.
- `git log -- .cursor/rules/ .claude/ CLAUDE.md skills/ agents/` for documentation-conventions evidence.
- Working-tree convention probes: presence and content of `pyproject.toml`, `package.json`, `.editorconfig`, `tsconfig.json`, `ruff.toml`, `mypy.ini`, `.github/workflows/**`, `tooling/deploy-manifest.json`, lint configs, formatter configs.
- Directory layout probe: top-level directory listing for project-shape signals (`src/`, `tests/`, `docs/`, etc.).

The skill stages these outputs in `_tmp_reflect_source3_<timestamp>.md` and passes the path to the agent via the brief's `source_3_*` constraints.

### Source 4 — plan docs, handoffs, dispatch logs

**Scanned by the skill via Glob.** Globs:

- `docs/plan/**/*.md`
- `docs/cross-memory/handoff*` (per requirements R3 — note the asterisk: also matches `handoff/`, `handoffs/`, `handoff*.md`)
- `docs/ops-dispatch-log*`

The skill collects matched paths and passes them to the agent via the brief's `source_4_*` constraints. The agent reads each file lazily as part of its distillation pass.

Bound: at most 50 files per glob to keep the agent's read budget bounded. Files past the bound are reported in the brief's `truncated:` field; the user is told in the report summary that some files were skipped.

### Source 1 — Claude Code `.jsonl` session transcripts

**Claude-Code-only, opt-in via flag.** Two flag shapes:

- `--from-session <id>` reads exactly one session at `~/.claude/projects/<active-slug>/sessions/<id>.jsonl` (or wherever Claude Code stores transcripts — see Risk below).
- `--since-last-reflect` reads all `.jsonl` files in the project's session directory whose modification time is newer than `state.toml.reflect.last_reflect_at`. Bound: at most 20 sessions per invocation; older sessions past the bound are reported as truncated.

**Risk — `.jsonl` format fragility.** Claude Code's `.jsonl` session transcript format is not a published public contract. The path, the file naming, the field shape, and the message-id mechanism are subject to change between Claude Code releases. A change Claude Code ships could silently break Source 1 ingestion in cross-memory v1.2.

**Mitigation / fallback strategy:**

- The skill runs a structural pre-check before dispatching the agent: verify the session file path exists, verify it parses as one JSON object per line, verify each line has the expected minimal keys (some structural shape — what counts as "expected" is the executor's call but should be the minimum needed to extract message text and id).
- If the pre-check fails, the skill emits a structured warning: `warning: transcript ingestion pre-check failed for session <id>: <reason>. Falling back to Sources 3 + 4 only.` The user sees the warning, the reflect run continues without Source 1, and the rest of the surface is unaffected.
- The skill records the pre-check result in the run summary. If a user reports consistent pre-check failures after a Claude Code upgrade, the executor (or the architect on a follow-up dispatch) updates the pre-check to match the new format. v1.2 source files are not coupled to a specific `.jsonl` shape; the pre-check is the load-bearing contract.

This is explicit acknowledgment of a known design risk — Source 1 is the most fragile of the four sources by construction. The mitigation makes the fragility graceful, not catastrophic.

### Source 5 — explicit seed

**Always available under any harness.** `--from <path>` accepts a file or directory. Multiple `--from` arguments are unioned. The skill validates each path exists and is readable; an invalid path errors per the requirements' edge case ("--from <path> points to a non-existent or unreadable path. reflect errors with a clear message identifying the path and exits without writing").

Bound: at most 100 paths total (combined `--from` set) or 10 MB total content size, whichever is smaller. Past the bound, the run errors with a clear message.

### Unification into the agent's input

The four sources feed the agent in parallel. The brief's `## Constraints` section lists the source set; the agent reads each independently during distillation. The agent is responsible for:

1. Reading the source files (using `Read`, `Glob`, `Grep`, `Bash` per its tool grants).
2. Generating raw candidates (the LLM-driven step — agent applies the taxonomy from R4).
3. Applying the deterministic filter (Section 2) before returning.

The skill is responsible for:

1. Resolving the source set from the user's flags.
2. Staging Source 3 outputs in `_tmp_*` files (since git commands are read-only Bash and the agent's Bash grants are even more restricted).
3. Building the brief.
4. Rendering the agent's output.
5. Running the interactive loop.

This division mirrors the existing audit pattern — the skill stages inputs and orchestrates UX; the agent does the synthesis.

### Out of scope

- A unified "source corpus" data structure passed to the agent. The agent reads each source path directly. No marshalling layer.
- Parallel source scanning. The skill scans sequentially; the source set is small enough that latency is dominated by the agent's distillation pass, not the source ingestion.

## 8. Staleness-Nudge Wiring in `init` and `doctor`

The hint fires when `(now - last_reflect_at) > reflect_staleness_threshold_days` and `last_reflect_at` is set.

### Where in `init`

The hint emits as the **last step before Step 5 (Summary output)**, after Step 4 completes. It is suggestive only — Step 5's summary line is unaffected by the hint's presence or absence. Verbose mode logs the hint check:

```
[init] step 4.5: reflect staleness check: last_reflect_at=2026-04-01T00:00:00Z, age=42 days, threshold=30 days → fire
[init] step 4.5: reflect staleness check: last_reflect_at=2026-05-10T00:00:00Z, age=3 days, threshold=30 days → suppress
[init] step 4.5: reflect staleness check: last_reflect_at=unset → suppress (first-run)
```

The hint text (verbatim, per R8): `Tip: it's been <N> days since reflect ran — run /cross-memory reflect to surface candidates.` The hint prints on its own line after the Step 4 verbose trace and before the Step 5 summary line.

### Where in `doctor`

The hint emits as a **footer line after the overall verdict**, regardless of mode (default / pre-deploy / post-deploy / targeted). The staleness check does not run as a doctor "check" with a verdict — it has no pass/fail/warn semantics; it is a UX nudge.

The hint position in the report is below the overall verdict:

```
Overall verdict: pass

Tip: it's been 42 days since reflect ran — run /cross-memory reflect to surface candidates.
```

In `--json` mode, the hint is included as a separate top-level field:

```json
{
  "schema_version": 1,
  "overall": "pass",
  ...
  "reflect_staleness_hint": {
    "fired": true,
    "days_since_last_reflect": 42,
    "threshold_days": 30,
    "message": "it's been 42 days since reflect ran — run /cross-memory reflect to surface candidates"
  }
}
```

When the hint suppresses (unset or under threshold), `reflect_staleness_hint.fired` is `false` and the `message` field is omitted.

### Cross-harness applicability

The staleness nudge is **fully harness-agnostic**. `init` and `doctor` already run under all three harnesses; the staleness check reads `~/.cross-memory/projects/<slug>/state.toml`, which is a canonical-store file present on every harness. There is no Claude-Code-specific path. The hint fires identically under Cursor and generic harnesses if the user has previously run `reflect` and the threshold is crossed.

### Threshold configuration

The threshold is `reflect_staleness_threshold_days` in `~/.cross-memory/config.yaml`. Default `30`. The check uses the active config value; there is no per-invocation override flag at v1.2 (a future `--staleness-days <N>` flag is a possible v1.3 addition but not required for the staleness nudge surface).

### Out of scope

- A `doctor --check reflect-staleness` targeted check. The hint is not a check with a verdict — adding it as a check would conflate diagnostics and UX nudges.
- Emitting the hint in `recall`, `list`, `search`, `audit`, or `save`. The hint surface is bounded to `init` and `doctor` deliberately — those two subcommands are the natural "I'm setting up / checking health" entry points where a nudge is welcome. Adding the hint to every subcommand would train users to ignore it.

## 10. Edge-Case Handling

The requirements doc enumerates 10 edge cases (§6). This ADD records the resolution for each — most are direct consequences of the architectural decisions above; a few warrant explicit notes.

| Edge case | Resolution |
| :--- | :--- |
| **Empty project (no git history, no `docs/plan/**`, no handoffs)** | Skill skips agent dispatch entirely. Emits `No candidates surfaced — no eligible input signal found.` Exits cleanly. `state.toml` is NOT written (per the empty-project rule in requirements §6 — no `reflect_declined.md`, but `state.toml` also not bumped because effectively no reflect run happened). |
| **N > 0 raw candidates, zero survive the filter** | Agent returns the list with `candidates surfaced: 0` and the per-reference-set drop counts. Skill renders the summary line `<N> candidates generated, all filtered as redundant against {canonical | archive | declined | excluded}.` and skips the interactive loop. `state.toml.reflect.last_reflect_at` IS updated — the reflect run completed successfully even though nothing was surfaced. The user's next `init` / `doctor` resets the staleness clock. |
| **Staleness nudge fired before reflect has ever run** | `last_reflect_at` is treated as unset. The hint MUST NOT fire (per R8 and AC8). Implementation: the staleness check reads `state.toml`; if the file is absent or the field is missing or unparseable, the check returns "unset" and the hint suppresses. |
| **Supersede collision on a memory the user just declined in this run** | The decline ledger takes precedence over the supersede check (per requirements §6). Implementation order in the filter: declined-redundancy check runs BEFORE the supersede flag computation. A candidate that matches a declined entry drops at the filter stage; the supersede check never sees it. The user is not asked twice. |
| **User runs `reflect --from-session <id>` under Cursor** | The skill errors at flag-parse time (Step 1 of the routing flow in Section 4): `error: --from-session is Claude-Code-only; current harness is cursor`. No agent dispatch, no `state.toml` write, no ledger touch. |
| **`--from <path>` to a non-existent or unreadable path** | Skill errors before dispatching the agent: `error: --from path <path> does not exist or is not readable`. Exits with no side effects. |
| **`--since-last-reflect` invoked when `last_reflect_at` is unset** | **Architect choice:** fall back to a bounded default window of last 30 days. Print an explanatory line: `info: --since-last-reflect requested but last_reflect_at is unset; scanning sessions from the last 30 days.` The default window is configurable via the same `reflect_staleness_threshold_days` config field (already in use elsewhere). Rationale: erroring would be less useful — the user clearly wants transcript ingestion; a bounded default window honors that intent without surprising them with a full-history scan. The 30-day default matches the staleness threshold so the user has only one number to reason about. |
| **User accepts a `save` flagged as `would-supersede`** | Routing enters the existing v1.1 supersede flow. The flag is just a renderer-side annotation in the report — once `save <id>` is invoked on a flagged candidate, the save pipeline detects the filename collision at Gate 4 (same as today) and presents the standard supersede UX. No new write path. |
| **User issues `done` with N candidates unactioned** | Unactioned candidates are recorded in the run log (in-memory only; never written to `reflect_declined.md`). They may re-surface on a subsequent run unless something else filters them out. This is by design — declining is an explicit user action. |
| **User issues `edit <id>` then aborts the edit** | No state change. The candidate remains in the in-memory report. The user may save / decline / edit it again, or issue `done`. Per the standard pattern, only confirmed actions write anything to disk. |

### Out of scope

- A `--dry-run` flag that walks the pipeline without writing `state.toml`. Out of scope for v1.2; the run summary already provides full visibility into what happened.
- A "what was filtered out" report mode beyond `--verbose`. Out of scope for v1.2; `--verbose` is enough.

  - Staleness nudge logic in `init` and `doctor`.

- **The agent (`agents/cross-memory.md` under `intent: distill`) owns:**
  - Reading source files.
  - Generating raw candidates.
  - Applying the deterministic filter.
  - Returning the structured candidate list.
  - Staging in `_tmp_*` during filter computation.

- **No new component is introduced.** v1.2 is entirely additive to the existing skill body and the existing agent contract.

## 12. Alternatives Considered & Rejected

This section gathers rejected alternatives that aren't already documented inline above.

### A separate `cross-memory-reflect` skill

**Considered:** Promoting `reflect` to a top-level skill of its own (`/cross-memory-reflect`).

**Rejected:** Reflect is a subcommand surface of cross-memory by design — it consumes the canonical store, reuses the save pipeline, shares the redaction surface, and dispatches the same agent. Splitting it into a separate skill would duplicate the adapter precedence chain, the lazy-provisioning logic, and the SC-21-enforced write surface. The `/cross-memory <subcommand>` shape is the right shape; reflect joins it as a peer of audit.

### A separate `intent: reflect` on the agent

**Considered:** Naming the new intent `reflect` to match the subcommand.

**Rejected:** The user-facing surface is the **subcommand** (`reflect`); the agent's job inside that surface is to **distill** candidates from sources. Naming the intent `distill` separates the action (what the user does) from the machine task (what the agent does). The audit precedent agrees — the user-facing subcommand is `audit`; the agent's intent is also `audit` because the names happen to match. For reflect, they do not match because the user reflects on a project while the agent distills candidates from artifacts. The naming choice is the same shape the v1 ADD used for `synthesize` (the agent's job inside the user-facing `recall` and synthesis flows — though `synthesize` happens to be its own surface in v1 because it has no direct user-facing equivalent subcommand).

### Auto-running reflect on staleness threshold cross

**Considered:** Make the staleness check actually invoke `/cross-memory reflect` when it fires.

**Rejected:** Per requirements R8 and AC9, "neither `init` nor `doctor` invokes `reflect`; they only print the hint." This is a hard constraint — auto-execution surprises the user. The hint surface is suggestive only.

### Storing `last_reflect_at` in `MEMORY.md` frontmatter

**Considered:** Adding `last_reflect_at:` to the per-scope `MEMORY.md` index file's frontmatter (which doesn't have frontmatter today).

**Rejected:** `MEMORY.md` has no frontmatter today; adding one would be a schema change to a file that participates in auto-injection on Claude Code. The risk of breaking auto-injection or sentinel-region invariants is real (per Decision 18 of the v1 ADD). The per-project `state.toml` is a structurally cleaner home.

### Inlining the four reference sets into a single combined corpus

**Considered:** Concatenate Reference Sets A + B + C + D into one flat list and run the filter against the combined corpus.

**Rejected:** The reference sets have different semantics — canonical store entries are user-saved facts, archive entries are formerly-saved, declined entries are explicitly rejected, and the categorical exclusion rule is a policy. Treating them as one corpus loses the per-set filter-reason annotation (the agent surfaces "dropped as declined" differently from "dropped as already canonical"). Per-set evaluation makes the run summary actionable.

### Allowing the agent to write `reflect_declined.md` directly

**Considered:** Let the agent append the decline entry instead of the skill.

**Rejected:** Decline events come from the interactive loop, which lives in the skill body. The agent has already returned by the time the user types `decline`. Pushing the write into a follow-up agent dispatch would double the agent-dispatch cost per reflect run and introduce a new write path that needs SC-21 verification. The skill-owned write is structurally simpler and the SC-21 surface is unchanged.

## 13. Open Item (b) — External-Trigger Contract (v1.3-deferred)

Per Q6 and R12, the non-interactive entry point is deferred to v1.3. This ADD does NOT design it — the requirement explicitly defers. The architect preserves the design intent here so v1.3 has a starting point:

- **Entry point shape:** `/cross-memory reflect --non-interactive --json` produces a structured JSON candidate list and exits without entering the interactive loop.
- **Exit codes:** `0 = candidates present`, `2 = no candidates`, `3 = staleness threshold not crossed (skipped)`, `4 = error`.
- **Trigger-context envelope:** `--context <path>` accepts a file describing the calling orchestrator's identity (name, run id, optional source-evidence pointer). The format is JSON. The agent's brief carries the context through unchanged so the candidate output can be correlated with the calling run.
- **Intended caller:** likely `/ops` end-of-run integration, but the v1.2 design must not couple to any specific caller. v1.3 designs the contract against a real concrete caller with driving requirements.

v1.2 does not implement any of the above. The argument grammar in Section 4 is intentionally extensible — adding `--non-interactive`, `--json`, and `--context <path>` in v1.3 does not require restructuring the existing flags.

## 15. Risks & Mitigations

| Risk | Specific failure mode | Mitigation in design |
| :--- | :--- | :--- |
| **`.jsonl` transcript format change** | Claude Code ships a new release that changes the transcript file format; Source 1 ingestion silently breaks or produces garbage. | Section 7 — pre-check validates structural shape before agent dispatch. Failure falls back to Sources 3 + 4 + 5 with a warning; the rest of the surface is unaffected. |
| **`~/.claude/CLAUDE.md` rule is missing or malformed** | The "What NOT to save" section is absent (the prerequisite was not closed before v1.2 shipped) or the user has removed/edited it incompatibly. | Section 1 — filter logs a structured warning and proceeds with an empty Reference Set D. AC12 verifies the section is present at acceptance time; the filter's graceful fallback prevents a v1.2 acceptance from blocking v1.2 use post-acceptance. |
| **Filter false negatives drown the user** | Conservative thresholds drop legitimate refinements; the user concludes `reflect` is useless. | Section 2 — balanced defaults (0.85 / 0.8 / 0.7) tuned to drop verbatim duplicates while letting refinements through. `--verbose` exposes filter decisions. Config-configurable per-machine. |
| **Filter false positives flood the user** | Permissive thresholds surface near-duplicates that should have been dropped; the user develops decline-fatigue. | Same as above — balanced defaults. Decline ledger persists, so each false positive only fires once across runs. |
| **`reflect_declined.md` grows unbounded** | Years of decline events accumulate in one file; reading it becomes slow. | Section 6 — append-only Markdown is cheap to read sequentially. Realistic ledger size after a year of weekly reflect runs is under 1 MB. Pruning is a v1.3+ addition if needed. |
| **State file corruption** | `state.toml` becomes unparseable (manual user edit gone wrong, partial write on power loss). | Section 3 — `init` and `doctor` treat unparseable `state.toml` as "unset" and suppress the hint. A subsequent `reflect` run rewrites the file from canonical truth at the end of the run. No persistent corruption surface. |
| **User runs `reflect` on a brand-new clone** | No git history, no `docs/plan/**`, no handoffs, no transcripts. Source 1 unavailable. | Section 10 — empty-project edge case returns the "no candidates surfaced" line cleanly. No spurious candidates, no `state.toml` bump, no `reflect_declined.md` creation. |
| **Cross-harness reflect divergence** | A user runs `reflect --from-session` under Claude Code, surfaces candidates from a session, then switches to Cursor and sees the same candidates re-surface from Sources 3+4 (because the session's content was committed to git in between). | Section 6 — declined entries in `reflect_declined.md` cross harness boundaries (it is a canonical-store file). A user who declines under Claude Code never sees the same candidate under Cursor. A user who **saves** under Claude Code never sees the candidate again either (canonical store reference set). Cross-harness divergence is bounded to "same content surfacing twice from different sources before either run completes" — a single-run edge case, not a persistent state issue. |
| **Source 1 transcript ingests sensitive content** | A session transcript contains an API key the user pasted; the agent distills it into a candidate and surfaces it. | The existing redaction pipeline (`redaction.md`) runs at Gate 2 of save. Even if a candidate body contains a secret, the save flow redacts before persisting. AND the user must explicitly type `save <id>` — there is no silent save path. The user has two checkpoints (the report's body-preview and the Gate 3 confirmation gate) to spot a secret before it lands on disk. |
| **Filter non-determinism** | The same inputs produce different candidate lists across runs because the agent's LLM step is stochastic. | The agent's brief specifies deterministic sort order (Section 5 Acceptance Criteria 2). The filter (Section 2) is purely deterministic. The LLM-driven raw-candidate-generation step is the only stochastic part, and the filter and sort downstream eliminate ordering and near-duplicate variation. AC15 verifies determinism end-to-end. |
| **The agent attempts to write `reflect_declined.md` directly** | An agent implementation invents a write path the architecture forbids. | The agent's allowlist already covers `~/.cross-memory/**`, so a write would not refuse-and-halt — but the **brief contract** in Section 5 explicitly states the agent does not write the ledger. The skill's interactive loop is the only write path. The verifier's SC-21 walk after v1.2 confirms no unintended write surfaces were introduced. |

## 16. Open Questions Remaining

After this ADD, two questions stay open and one is acknowledged as deferred-by-design.

### OQ-v1.2-1 — `~/.claude/CLAUDE.md` "What NOT to save" rule wording

**Why still open.** Section 1 picks the rule's location but does not write its content. The exact wording is a documentor task at execute time, ideally informed by real decline-ledger data — which won't exist until v1.2 has been running for a while. v1.2 ships with a "starter wording" that the executor and documentor produce; a follow-up doc-sync pass refines it after the first 30 days of decline-ledger evidence. **Resolution path:** documentor writes the starter section at v1.2 implementation time; a v1.3 (or v1.2.1 patch) refines the wording against real decline data.

### OQ-v1.2-2 — Calibration of anti-redundancy thresholds against real data

**Why still open.** The defaults in Section 2 are reasoned, not measured. The reasoning is sound, but the only way to validate the thresholds is to run `reflect` on real projects and observe the rate of legitimate refinements being dropped (false negatives) versus near-duplicates being surfaced (false positives). **Resolution path:** after 30 days of v1.2 use across at least three projects, the architect re-dispatches with measured workload data — count of declines, count of saves, count of "user complained the filter dropped something important." Adjustments are config-configurable in the meantime.

### OQ-v1.2-3 — External-trigger / post-run-hook contract (deferred by design)

**Why still open.** Per Open Item (b) and R12, the non-interactive entry point and exit-code contract are deferred to v1.3. The architect must not design against a hypothetical caller. **Resolution path:** v1.3 architect dispatch, ideally driven by `/ops` end-of-run integration as the concrete caller — that orchestrator will be the first to need the contract.
