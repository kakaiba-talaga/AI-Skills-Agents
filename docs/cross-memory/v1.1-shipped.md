# Cross-Memory v1.1 — Shipped Artifact Traceability

This document is the closing artifact of the cross-memory v1.1 build. It records what shipped, what was deferred, how the acceptance gate works, and how the seven scenario contracts that were contract-only verified at v1 are now reachable as behavioral checks. For v1 surface traceability see `docs/cross-memory/v1-shipped.md`; for full context see `docs/cross-memory/requirements.md`, `docs/cross-memory/architecture-decision.md`, and the v1.1 skill surface at `skills/cross-memory/SKILL.md`.

---

## Shipped

Cross-memory v1.1 adds three surface areas to the v1 skill: the `init` subcommand, the `doctor` subcommand, and the bare-invocation hint behavior. Two supporting sections accompany them — the check-name vocabulary (a stable identifier registry for doctor checks) and shared flag parsing (flag definitions reused across `init` and `doctor`). All v1 artifacts remain unchanged.

### init subcommand (`skills/cross-memory/SKILL.md → ## Subcommand: init`)

Bootstraps `~/.cross-memory/` and registers the active harness sentinel block. Init is additive only — it never deletes, overwrites, or repairs existing files.

**Five-step sequence:**

| Step | What happens |
| :--- | :--- |
| Step 1 — Provisioning | Calls the lazy-provisioning sequence eagerly. No-op if `~/.cross-memory/` already exists. Delegates entirely to `## Config → Lazy-provisioning sequence` — no new directory or config logic. |
| Step 2 — Adapter detection | Runs the five-step precedence chain to determine the active harness. Records both the harness name and the winning precedence step for the summary. Read-only. |
| Step 3 — Reachability probe | Runs `adapter-detection` and `sentinel-marker-count` (Group C) in read-only mode against the harness-native `MEMORY.md`. A failure produces a structured warning and continues. |
| Step 4 — Always-on filter + sentinel write | Invokes the always-on tier filter, passes the result to the injection-block formatter, then dispatches `update_sentinel_block`. Under `cursor` and `generic` harnesses, the write is a no-op per the adapter contract; `sentinel-region-content-parses` (Group C) returns `not-applicable`. After writing under `claude-code`, runs `sentinel-region-content-parses` as a self-check — a `fail` here aborts before step 5. |
| Step 5 — Summary output | Emits the human summary line, JSON (when `--json`), or verbose trace (when `--verbose`). Reads accumulated state from steps 1–4; makes no writes. |

**Command syntax:**

```
/cross-memory init \
  [--harness <claude-code|cursor|generic>] \
  [--scope <user-global|project:<slug>|harness:<name>>] \
  [--json] \
  [--verbose]
```

**Flags:** `--harness`, `--scope`, `--json`, `--verbose` are defined in `## Shared flag parsing`. There is no `--repair`, `--force`, or `--reset` flag.

**Idempotency contract.** Init is safe to run repeatedly. Step 1 skips if the store is present; step 4 skips the write if the computed sentinel content is byte-identical to the current content. The human summary distinguishes `store=already-present` and `sentinel=already-current (no change)` so a defensive re-run is visibly a no-op.

**What init does NOT do:**

- No codebase-fact distillation — zero LLM calls; the `--discover` flag is deferred.
- No agent dispatch — runs entirely in the skill body; the cross-memory agent's lane allowlist is unchanged.
- No save — never creates or modifies canonical memory files under `~/.cross-memory/`.
- No `--repair` or `--force` — bad-state diagnosis and repair are doctor's lane.
- No telemetry — no usage data, no network calls.
- No deploy integration — not invoked by `tooling/deploy.{ps1,sh}`.
- No project-scope provisioning — project-scope `MEMORY.md` is still created lazily on first save.

**Reuse of doctor's check primitives.** The shared contract is a documentation contract: any check identifier that appears in both subcommands means the same finding regardless of which subcommand surfaces it. Init reuses three check points from the `## Check-name vocabulary`:

1. After step 1: optionally runs `canonical-archive-not-indexed` and `canonical-memory-md-consistency` (Group A) as read-only probes. Failures surface as structured warnings; init does not abort.
2. Step 3 (reachability probe): runs `adapter-detection` (Group E) and `sentinel-marker-count` (Group C) in read-only mode.
3. After step 4 (sentinel write): runs `sentinel-region-content-parses` (Group C) as a self-check. A `fail` here causes init to fail fast before step 5.

### doctor subcommand (`skills/cross-memory/SKILL.md → ## Subcommand: doctor`)

Read-only structural and integration health check. Doctor inspects the canonical store, sentinel blocks, redaction surface, mirror consistency, and adapter-detection state. It never writes, repairs, or auto-corrects.

**Command syntax:**

```
/cross-memory doctor \
  [--pre-deploy | --post-deploy] \
  [--check <name>] \
  [--harness <claude-code|cursor|generic>] \
  [--scope <user-global|project:<slug>|harness:<name>>] \
  [--json] \
  [--verbose]
```

**Four modes:**

| Mode | Invocation | Check set |
| :--- | :--- | :--- |
| Default | No mode flag | Groups A–D fully; Group E `adapter-detection` only. Excludes deploy-manifest, stale-artifact, cross-harness round-trip, and SC behavioral walk. Wall-clock budget: under 5 seconds on a 100-memory store. |
| Pre-deploy | `--pre-deploy` | Six-check shorthand: `canonical-frontmatter-parse`, `canonical-memory-md-consistency`, `sentinel-marker-count`, `redaction-denylist-parses`, `deploy-manifest-coverage`, `stale-shipped-artifacts`. Suitable as CI preflight before `tooling/deploy.{ps1,sh}`. |
| Post-deploy | `--post-deploy` | Five checks: `mirror-canonical-source-exists`, `mirror-detect-collisions`, `sentinel-region-content-parses` (harness-applicability applies), `adapter-detection`, `sc-behavioral-walk`. Designed to run from the second harness after a successful deploy. |
| Targeted | `--check <name>` | Exactly the named checks — no implicit additions. Accepts individual check identifiers or Group identifiers (`canonical-integrity`, `mirror-consistency`, `sentinel-markers`, `redaction-surface`, `deploy-target-prep`). Mutually exclusive with `--pre-deploy` / `--post-deploy`. |

**Five check groups (Groups A–E):**

| Group | Identifier | Checks | Harness scope |
| :--- | :--- | :--- | :--- |
| A | `canonical-integrity` | `canonical-frontmatter-parse`, `canonical-slug-derivation`, `canonical-memory-md-consistency`, `canonical-no-duplicate-slugs`, `canonical-archive-not-indexed` | All harnesses |
| B | `mirror-consistency` | `mirror-sidecar-frontmatter-agreement`, `mirror-canonical-source-exists`, `mirror-detect-collisions` | All harnesses; read-only |
| C | `sentinel-markers` | `sentinel-marker-count`, `sentinel-region-bytes-fingerprint`, `sentinel-region-content-parses` | `claude-code` runs normally; `cursor` and `generic` return `not-applicable` (no sentinel region exists) |
| D | `redaction-surface` | `redaction-denylist-parses`, `redaction-sampling-scan`, `redaction-overridden-flag-audit` | All harnesses |
| E | `deploy-target-prep` / `cross-harness-validation` | `deploy-manifest-coverage`, `stale-shipped-artifacts`, `cross-harness-roundtrip`, `adapter-detection`, `sc-behavioral-walk` | Pre-deploy checks: all harnesses. Post-deploy cross-harness checks: harness-applicability applies per SC. |

**Output formats:**

- **Human-readable report** — structured markdown to chat; one section per check group with a per-section verdict and a final overall verdict line.
- **JSON report** (`--json`) — single JSON object; schema version 1; top-level keys `schema_version`, `timestamp_utc`, `harness`, `harness_selection_step`, `active_project_slug`, `overall`, `sections`.

**Verdict aggregation.** Five values: `pass`, `warn`, `fail`, `error`, `not-applicable`. Ordering: `not-applicable = pass < warn < fail < error`. A section composed entirely of inapplicable checks reports `not-applicable`; at the overall-verdict level that counts as `pass`. Exit codes apply only when `--json` is set: 0 = pass / not-applicable, 1 = warn, 2 = fail, 3 = error.

**Read-only by default.** Doctor is read-only at v1.1. There is no `--repair`, no `--fix`, and no auto-correction. Doctor is skill-only; the cross-memory agent is not invoked.

### Bare-invocation behavior (`skills/cross-memory/SKILL.md → ### Bare-invocation sequence`)

When `/cross-memory` is invoked with no subcommand, the skill:

1. Runs a read-only probe to determine the active harness and inspect the canonical store state and (on Claude Code) the sentinel block.
2. Emits the structured usage block (the same block as `help`).
3. Conditionally appends a first-run hint:
   - **Claude Code:** hint fires if `~/.cross-memory/` is absent **or** the active sentinel block is missing or empty. Hint text: `Tip: run /cross-memory init to bootstrap this project.`
   - **Cursor / generic:** hint fires only if `~/.cross-memory/` is absent (sentinel-block predicate suppressed). Hint text: `Tip: run /cross-memory init to bootstrap (Cursor injection surface deferred to post-v1).`
   - Hint is suppressed when neither condition applies.
4. Stops. The skill never auto-runs init from bare invocation.

### Check-name vocabulary (`skills/cross-memory/SKILL.md → ## Check-name vocabulary`)

A stable identifier registry for doctor checks and init's check-reuse points. Renaming any identifier is a breaking change; new checks are pure-add.

| Group | Check name |
| :--- | :--- |
| A — `canonical-integrity` | `canonical-frontmatter-parse`, `canonical-slug-derivation`, `canonical-memory-md-consistency`, `canonical-no-duplicate-slugs`, `canonical-archive-not-indexed` |
| B — `mirror-consistency` | `mirror-sidecar-frontmatter-agreement`, `mirror-canonical-source-exists`, `mirror-detect-collisions` |
| C — `sentinel-markers` | `sentinel-marker-count`, `sentinel-region-bytes-fingerprint`, `sentinel-region-content-parses` |
| D — `redaction-surface` | `redaction-denylist-parses`, `redaction-sampling-scan`, `redaction-overridden-flag-audit` |
| E — `deploy-target-prep` | `deploy-manifest-coverage`, `stale-shipped-artifacts` |
| E — `cross-harness-validation` | `cross-harness-roundtrip`, `adapter-detection`, `sc-behavioral-walk` |

The five valid Group identifiers for `--check <group>` are: `canonical-integrity`, `mirror-consistency`, `sentinel-markers`, `redaction-surface`, `deploy-target-prep`. The `cross-harness-validation` group is post-deploy-only and is rejected as a `--check` argument in targeted mode.

### Shared flag parsing (`skills/cross-memory/SKILL.md → ## Shared flag parsing`)

These four flags are accepted by both `init` and `doctor`. They are defined once and referenced per subcommand rather than redefined.

| Flag | Semantics |
| :--- | :--- |
| `--harness <claude-code\|cursor\|generic>` | Overrides adapter selection for the invocation. Wins as Step 1 of the five-step precedence chain. Unknown values fail fast with a structured error. |
| `--scope <user-global\|project:<slug>\|harness:<name>>` | Restricts the subcommand's operation to a single scope. Patterns are the same as the `scope` frontmatter field. A bare `project` or `harness` without the colon-and-slug suffix is invalid. |
| `--json` | Requests machine-readable output. The subcommand emits a JSON document instead of the default human-readable prose. Boolean — takes no argument. |
| `--verbose` | Requests additional diagnostic output. Prints the harness selection step on the first output line; subcommands may emit per-step detail. Boolean — takes no argument. |

## Deferred (post-v1.1)

| Item | Reason deferred |
| :--- | :--- |
| `--discover` flag for init | Requires LLM-driven codebase-fact distillation — zero LLM calls is v1.1's design constraint. Deferred to a future flag. |
| `--repair`, `--force`, `--reset` for init | Any modification to existing files is explicitly out of scope for init at v1.1. Bad-state repair belongs to doctor's future `--repair` / `--fix` path. |
| `--repair` / `--fix` for doctor | Doctor is read-only at v1.1. The diagnostic-then-fix workflow is explicit; auto-repair would conflate diagnosis and mutation. |
| `--trace` flag (any trace instrumentation) | Not scoped in v1.1. Post-v1.1. |
| Cursor full sentinel-block injection surface | `update_sentinel_block` is a documented v1 no-op in `adapter-cursor.md § 6`. The always-on filter runs on Cursor, but no sentinel-block bytes are written. Full injection surface is deferred to post-v1. |
| `tooling/transform-cursor-cross-memory.{ps1,sh}` | A contingent path: required only if integration testing surfaces a Cursor-specific slash-command syntax requirement. Not in the v1.1 deliverable — see the Cursor parity note below. |
| Telemetry | No usage data, no network calls, same posture as v1. |
| Deploy integration for init | Init is not invoked by `tooling/deploy.{ps1,sh}` and does not invoke them. Post-v1.1. |
| Project-scope provisioning | The project-scope `MEMORY.md` for the active project is still created lazily on first save. Init does not provision project-scope memory files. |
| Cross-session reflection subcommand | Deferred post-v1.1. Requires three design questions resolved before scoping: input data source, cadence, and pattern taxonomy. Depends on the v1 surface being behaviorally validated first. See `docs/cross-memory/v1-shipped.md → ## Deferred` for the full deferral note. |

## SC verification closures

At v1, seven scenario contracts (SC-1 through SC-5, SC-15, SC-16) were verified at the contract level through static walks against the adapter contracts in `SKILL.md` and the three adapter files. Behavioral end-to-end coverage required deploying via `tooling/deploy.ps1` and running a fresh-session regression pass.

**v1.1 closes these seven SCs behaviorally via `doctor`'s `sc-behavioral-walk` check.** The check walks each SC as a small in-place behavioral probe; harness-specific applicability determines which SCs run, which delegate, and which return `not-applicable`.

| SC | What it verifies | Under Claude Code | Under Cursor |
| :--- | :--- | :--- | :--- |
| SC-1 | User-global preference surfaces in a different project | Walked behaviorally — confirms `[CROSS-MEMORY]` block contains the user-global entry | **`not-applicable`** — `update_sentinel_block` is a v1 no-op; the block does not exist on the Cursor side |
| SC-2 | Cross-harness round-trip | Delegates to `cross-harness-roundtrip` (post-deploy). Walked behaviorally. | Delegates to `cross-harness-roundtrip` (post-deploy). Walked behaviorally — exercises canonical-store + mirror surfaces. |
| SC-3 | Auto-propose flow surfaces a memory candidate | Walked behaviorally | Walked behaviorally |
| SC-4 | Save / recall round-trip on canonical store | Walked behaviorally | Walked behaviorally |
| SC-5 | List / forget / search round-trip on canonical store | Walked behaviorally | Walked behaviorally |
| SC-15 | `<private>` redaction suppresses content from always-on tier output | Walked behaviorally — confirms redacted content does not appear in the `[CROSS-MEMORY]` block | **`not-applicable`** — the block is absent at v1; redaction remains contract-verified via Group D `redaction-sampling-scan` |
| SC-16 | `[CROSS-MEMORY]` injection block format is correct | Walked behaviorally — `sentinel-region-content-parses` is the same primitive | **`not-applicable`** — same reason as SC-1 |

Under `--harness claude-code`, `sc-behavioral-walk` emits seven sub-findings. Under `--harness cursor`, it emits four behavioral sub-findings (SC-2 through SC-5) and three `not-applicable` sub-findings (SC-1, SC-15, SC-16) with `reason: "cursor injection surface (update_sentinel_block) is a documented v1 no-op"`. Doctor's overall-verdict aggregation treats `not-applicable` as `pass`, so an otherwise-healthy Cursor walk returns overall `pass`.

The full v1 SC table (SC-1 through SC-21) and v1 verifier closures are in `docs/cross-memory/v1-shipped.md → ## Verified Success Criteria`.

## Cursor parity assumption

Cursor slash-command parity — whether `/cross-memory <subcommand>` parses correctly in Cursor's composer — is verified at deploy time as part of the cross-harness acceptance gate. If `/cross-memory <subcommand>` does not parse in Cursor's composer, a `tooling/transform-cursor-cross-memory.{ps1,sh}` transform is required. That transform is a **deferred contingent path** and is not part of the v1.1 deliverable. The gate procedure in the next section records where this check lives.

## Acceptance gate

The v1.1 acceptance gate runs in three stages. Operator-facing procedure details are in `skills/cross-memory/SKILL.md → ## Subcommand: doctor → #### Post-deploy walk (Claude Code)` and `#### Post-deploy walk (Cursor)`.

### Step 0 — Preconditions (Claude Code)

Before the gate walks, confirm that a healthy canonical store exists and that a project-scope memory is present:

1. Confirm `~/.cross-memory/` exists. If absent, run `/cross-memory init`.
2. Confirm at least one project-scope memory (type `project`, scope `project:<slug>`) is in the canonical store.
3. Save a test memory from the Claude Code harness. This memory serves as the cross-harness round-trip target in Step 2.

### Step 1 — Doctor walk in Claude Code

Run the post-deploy check from Claude Code:

```
/cross-memory doctor --post-deploy --harness claude-code
```

Assert the following before moving to Step 2:

- `mirror-canonical-source-exists` and `mirror-sidecar-frontmatter-agreement` → `pass`
- `sentinel-region-content-parses` → `pass`
- `sc-behavioral-walk` sub-findings for SC-1, SC-3, SC-4, SC-5, SC-15, SC-16 → `pass` (SC-2 returns `not-applicable` in a single-harness invocation and is excluded from aggregation here)
- Overall verdict → `pass`

A `warn` or `fail` must be resolved before proceeding to Step 2.

### Step 2 — Doctor walk in Cursor (cross-harness round-trip)

Run the post-deploy check from the Cursor harness, using the test memory saved in Step 0:

```
/cross-memory doctor --post-deploy --harness cursor
```

Assert the following:

- `mirror-canonical-source-exists`, `mirror-detect-collisions`, `adapter-detection` → `pass`
- `sentinel-marker-count` and `sentinel-region-content-parses` → `not-applicable` (Cursor `update_sentinel_block` is a documented v1 no-op — a `fail` here indicates an unexpected marker)
- `cross-harness-roundtrip` → `pass` (the canonical path of the Step 0 test memory is locatable from Cursor — this is the behavioral walk of SC-2)
- `sc-behavioral-walk` sub-findings: SC-2, SC-3, SC-4, SC-5 → `pass`; SC-1, SC-15, SC-16 → `not-applicable`
- Overall verdict → `pass`

If `/cross-memory <subcommand>` does not parse in Cursor's composer during this step, a `transform-cursor-cross-memory` script is required (see Cursor parity assumption above).
