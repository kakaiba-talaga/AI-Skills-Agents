# Requirements: Cross-Memory v1.2 — `reflect` Subcommand and `distill` Intent

> **Revision history.**
>

> - **2026-05-13 r1** — Initial deliverable (locked Step 5.5 of interview).

## Summary

Cross-memory v1.2 adds a recurring, out-of-session, additive, proactive discovery surface to the existing cross-memory system. It introduces a new `/cross-memory reflect` subcommand (human-facing) and a new `intent: distill` on the `cross-memory` agent (machine-facing), together producing candidate memories from artifacts the user has already created (git history, plan docs, handoffs, optionally session transcripts) and presenting them through an interactive audit-style report.

The release is strictly additive over v1 + v1.1. SC-21 holds unchanged — the agent's write allowlist remains exactly `~/.cross-memory/**`, sentinel-bounded MEMORY.md at `~/.claude/projects/<active-slug>/memory/MEMORY.md`, and `_tmp_*`. No existing behavior is modified. The external-trigger / post-run-hook contract is deferred to v1.3, where it will be designed against a real concrete caller.

This document is the synthesis of six interview rounds plus a Step 5.5 success-criteria lock. All twelve success criteria are user-confirmed and locked.

## Scope

### In scope

- New subcommand `/cross-memory reflect` with on-demand invocation and an interactive audit-style report loop (`save` / `decline` / `edit` / `done`).
- New `intent: distill` on the `cross-memory` agent, writing only to the existing SC-21 allowlist.
- Default auto-scan inputs: git history + working-tree conventions (Source 3) and `docs/plan/**`, `docs/cross-memory/handoff*`, `docs/ops-dispatch-log*` (Source 4).
- Opt-in transcript ingestion under Claude Code only (Source 1) via `--from-session <id>` or `--since-last-reflect`.
- Always-available explicit seed (Source 5) via `--from <path>`.
- Pattern taxonomy enforced to exactly four categories: architectural decisions; conventions implicit in code; workflow patterns from successful runs; user preferences from feedback patterns.
- Deterministic post-generation anti-redundancy filter against four reference sets (canonical store, archive, new `reflect_declined.md` ledger, "What NOT to save" categorical rule).
- New per-project `reflect_declined.md` ledger written by the agent inside the SC-21 allowlist.
- Staleness nudge surfaced by `init` and `doctor` when `last_reflect_at` exceeds a configurable threshold (default 30 days).
- Cursor and generic harness parity using Sources 3+4+5 only (no transcript ingestion).
- Closure of the "What NOT to save in memory" doc gap before v1.2 ships.

### Out of scope

- **Project goals as a pattern category.** Project goals are project-specific and may differ across projects; if anything in that category is durably relevant it reduces to user preferences. Emitting a project-goal candidate is a filter violation, not a feature.
- **External-trigger / post-run-hook contract** (non-interactive entry point, exit-code contract, trigger-context envelope). Deferred to v1.3 — see Open Items (b).
- **Binding `reflect` to any specific orchestrator** (`/ops`, `/ralph-loop`, etc.). The post-run-hook concept is endorsed conceptually but not bound to any specific caller in v1.2.
- **Auto-execution of `reflect`.** The staleness nudge is suggestive only; it never invokes `reflect` without the user's explicit command.
- **Unprompted full-history transcript scans** under any harness. Transcript ingestion is always opt-in and bounded.
- **Modifications to v1 or v1.1 success criteria.** v1.2 is additive only; zero regressions required (see Requirement 12).
- **Widening of the SC-21 allowlist.** The new intent must write only to existing allowed paths.

## 1. Goals and Non-Goals

### Goals

| # | Goal | Concrete shape |
| :--- | :--- | :--- |
| G1 | Proactive discovery of durable memories | A user who has done work but not saved memories can run one command and review N machine-proposed candidates with source evidence |
| G2 | Strict additivity over v1 + v1.1 | All twenty-one v1 success criteria and all v1.1 behavioral closures remain green after v1.2 lands |
| G3 | Harness portability of the human-facing surface | `/cross-memory reflect` runs under Claude Code, Cursor, and generic harnesses with feature-flagged transcript ingestion |
| G4 | Anti-noise by construction | A deterministic post-generation filter prevents re-proposing memories the user already has, archived, or declined |
| G5 | Explicit user control over writes | Per-candidate confirmation defaults to **N**; supersedes are flagged and require explicit user choice; no silent saves, no silent supersedes |

### Non-Goals (explicit)

- **Not a fully automated memory writer.** `reflect` proposes; the user disposes.
- **Not an event-driven hook.** v1.2 ships only on-demand invocation plus a staleness hint; orchestrator integration is v1.3 design space.
- **Not a transcript archive.** Transcripts are read, distilled, and discarded; only candidate metadata and the user's accept/decline decisions are persisted.

## 2. Requirements

### R1. New `reflect` subcommand (Q4)

- A new subcommand `/cross-memory reflect` exists in `skills/cross-memory/SKILL.md` and is documented in `skills/cross-memory/README.md`.
- Invocation is on-demand only. Neither `init`, `doctor`, nor any other subcommand auto-executes `reflect`.
- The subcommand produces a single audit-style report listing **all** N candidates that survive the anti-redundancy filter, with the following per-candidate columns: `id`, `type`, `category`, `scope`, `proposed-name`, `body-preview` (truncated to a bounded character limit chosen by the architect), and `source-evidence` (a stable pointer such as a commit SHA, file path + line range, or transcript message id).
- The report enters an interactive loop accepting four commands per candidate: `save <id>`, `decline <id>`, `edit <id>`, `done`.
- `save <id>` flows through the existing save pipeline (Gate 3 → Gate 4) defined in `skills/cross-memory/SKILL.md`.
- `decline <id>` appends a structured entry to the per-project `reflect_declined.md` ledger (see R6).
- `edit <id>` opens a minimal field-tweak surface (name, body, tags, scope) and re-enters Gate 3 on confirmation.
- `done` exits the loop. Candidates neither saved, declined, nor edited at exit are recorded as "unactioned" in the run log but NOT written to `reflect_declined.md`.
- The per-candidate confirmation default is **N** (conservative). The user must take explicit action to save.

### R2. New `distill` intent on the `cross-memory` agent (Q-cross-cutting)

- The `cross-memory` agent definition at `agents/cross-memory.md` gains a new `intent: distill` alongside the existing `audit` intent.
- The `distill` intent's write allowlist is **identical** to SC-21: `~/.cross-memory/**`, sentinel-bounded MEMORY.md at `~/.claude/projects/<active-slug>/memory/MEMORY.md`, and `_tmp_*`. No new paths.
- The intent's brief shape is documented under `skills/ops/brief-contract.md` and `agents/cross-memory.md` consistent with the v1.1 audit-brief precedent.
- The intent is invoked by `/cross-memory reflect` and is the only path through which candidates are generated.

### R3. Default auto-scan inputs (Q1)

- Under all harnesses, `reflect` ingests by default:
  - **Source 3** — git history (commit messages, diff stats, author identity) and working-tree conventions discoverable from the checkout (lint config, formatter config, directory layout).
  - **Source 4** — `docs/plan/**`, `docs/cross-memory/handoff*`, `docs/ops-dispatch-log*` (any project-root-relative path matching these globs).
- Under Claude Code only, the user may opt in to:
  - **Source 1** — `.jsonl` session transcripts under `~/.claude/projects/<active-slug>/`, via either `--from-session <id>` (named session) or `--since-last-reflect` (all sessions newer than `last_reflect_at`).
- Always available under any harness:
  - **Source 5** — `--from <path>` accepts a user-supplied file or directory as an explicit seed.
- Under Cursor and generic harnesses, Sources 1 is unavailable; Sources 3+4+5 only. Behavior is otherwise parity-equivalent.
- An unprompted full transcript scan is never performed under any harness.

### R4. Pattern taxonomy (Q3)

- Candidates surfaced by `distill` belong to exactly one of these four categories:
  - **architectural-decisions** — durable choices about structure, technology, or boundaries.
  - **conventions-implicit-in-code** — patterns the code follows that are not written down (e.g., "all API errors return `{error, code, context}`").
  - **workflow-patterns-from-successful-runs** — repeatable sequences observable in plan docs or ops logs that worked.
  - **user-preferences-from-feedback-patterns** — explicit or strongly implied user preferences observable across feedback events.
- Project goals are **explicitly excluded**. A candidate whose category resolves to project goal MUST be dropped by the filter and is treated as a filter violation if it reaches the user-facing report.

### R5. Post-generation deterministic anti-redundancy filter (Q5)

- A post-generation deterministic anti-redundancy filter drops candidates whose **slug-overlap + tag-overlap + body-token Jaccard** exceeds threshold against **three deterministic reference sets — the canonical store filtered to relevant tiers, `~/.cross-memory/archive/`, and the new per-project `reflect_declined.md` ledger — plus one LLM-prompt-applied exclusion corpus drawn from `~/.claude/CLAUDE.md`'s `## What NOT to save in memory` section.** The deterministic filter operates over the three structured reference sets; the LLM-prompt-applied corpus suppresses candidates categorically during raw-candidate generation, before the deterministic filter sees the candidate list.
- **Reference Set A — canonical store** (deterministic). Filtered to relevant tiers for the current run: active project's `project:<slug>` plus active harness's `harness:<name>` plus `user-global`.
- **Reference Set B — archive** (deterministic). All entries under `~/.cross-memory/archive/`.
- **Reference Set C — per-project decline ledger** (deterministic). The new `reflect_declined.md` for the active project (see R6).
- **Reference Set D — "What NOT to save" categorical exclusion corpus** (LLM-prompt-applied). A stable readable codified rule (see R10) drawn from `~/.claude/CLAUDE.md`'s `## What NOT to save in memory` section. Consumed by the agent during raw-candidate generation as a system-prompt input; does NOT feed the deterministic filter.
- Thresholds for slug-overlap, tag-overlap, and body-token Jaccard are configurable; defaults are architect-calibrated (see Open Items (c)).
- The deterministic filter is purely post-generation against Sets A/B/C; it does not influence which sources are read. The LLM-prompt-applied corpus (Set D) acts categorically during raw-candidate generation, before the deterministic filter runs.

### R6. Per-project `reflect_declined.md` ledger (Q5)

- A new file `reflect_declined.md` is created lazily on first decline at `~/.cross-memory/projects/<slug>/reflect_declined.md`.
- The agent's writes to this file remain inside the SC-21 allowlist (`~/.cross-memory/**`).
- Each decline appends a structured entry containing at minimum: timestamp (ISO 8601 UTC), candidate `id`, `proposed-name`, `category`, `scope`, `body-preview`, and `source-evidence` pointer.
- The ledger is consulted by Reference Set C in R5; identical proposals on subsequent runs are filtered out.

### R7. Supersede handling (Q4)

- When a generated candidate matches an existing canonical-store entry strongly enough to be considered a supersede (using the same overlap signals as R5 but evaluated independently of the drop threshold), the candidate appears in the report flagged `would-supersede <existing-id>`.
- The user must explicitly enter the supersede branch (via `save` on a flagged candidate prompting the existing supersede flow defined in v1.1) or skip.
- Silent supersedes are forbidden. The supersede flag is rendered in the report column set described in R1.

### R8. Staleness nudge in `init` and `doctor` (Q2)

- `init` and `doctor` read `last_reflect_at` (storage location chosen by the architect — see Open Items (d)).
- When the difference between current time and `last_reflect_at` exceeds the configurable threshold (default 30 days), both subcommands emit a single-line hint: "Tip: it's been N days since `reflect` ran — run `/cross-memory reflect` to surface candidates."
- The hint is suggestive only. Neither `init` nor `doctor` invokes `reflect`.
- When `last_reflect_at` is unset (no prior run), the hint MUST NOT fire — see Edge Cases.

### R9. Cross-harness parity (Q1, cross-cutting)

- Under Cursor and generic harnesses, `reflect` operates on Sources 3+4+5 only; the `--from-session` and `--since-last-reflect` flags are either absent from the harness-specific README or documented as Claude-Code-only.
- All other behavior (report shape, command loop, taxonomy, anti-redundancy filter, decline ledger, supersede flag, staleness nudge) is identical across harnesses.

### R10. "What NOT to save in memory" prerequisite (Q5, ADD-gated)

- Before v1.2 ships, a stable readable codification of the "What NOT to save in memory" rule MUST exist at one of two addressable locations chosen by the architect during the ADD: `~/.claude/CLAUDE.md` or the v1.2 spec under `docs/cross-memory/`.
- Reference Set D of R5 references this codified rule.
- This is a prerequisite — the rule's home is selected by the architect, but its existence is a v1.2 acceptance bar (not deferrable).

### R11. v1.2 additive only; no regressions

- All v1 success criteria SC-1 through SC-21 remain green.
- All v1.1 behavioral closures (per `docs/cross-memory/v1.1-shipped.md`) remain green.
- No existing subcommand changes its observable contract.

### R12. Deferred external-trigger surface (Q6)

- v1.2 ships only the human-facing on-demand surface (`/cross-memory reflect`) plus the staleness nudge.
- The non-interactive entry point, exit-code contract, and trigger-context envelope are explicitly deferred to v1.3 — see Open Items (b).
- v1.2 documentation MUST state the deferral so downstream readers do not interpret silence as a feature gap.

## 3. Constraints

- **SC-21 unchanged.** The `cross-memory` agent's write allowlist remains exactly `~/.cross-memory/**`, sentinel-bounded MEMORY.md at `~/.claude/projects/<active-slug>/memory/MEMORY.md`, and `_tmp_*`. The new `intent: distill` writes only to these paths.
- **Additive only.** No v1 or v1.1 contract is altered. Zero regressions required.
- **No silent writes.** Every persisted memory either originated from explicit `save <id>` in the reflect loop or from the existing `/cross-memory save` path, both of which flow through Gate 3 → Gate 4.
- **No auto-execution.** The staleness nudge never invokes `reflect`. The user runs it deliberately.
- **No unprompted transcript scans.** Transcript ingestion under Claude Code requires `--from-session <id>` or `--since-last-reflect`; full-history scans without flags are forbidden.
- **Harness portability.** Sources 1 may be absent under non-Claude-Code harnesses; the rest of the surface is parity-equivalent.
- **Deterministic filter.** R5's filter must be reproducible across runs given the same inputs and reference sets — no stochastic ordering, no time-dependent randomness.
- **Bounded body previews.** Report body-preview length is architect-chosen and consistent across runs.
- **Project files only.** Skill/agent file edits stay under `skills/cross-memory/`, `agents/cross-memory.md`, `docs/cross-memory/`, and `skills/ops/brief-contract.md` per the project's documentation map; no scope creep into unrelated skills.

## 6. Edge Cases

- **Empty project (no git history, no `docs/plan/**`, no handoffs).** `reflect` returns a report with zero candidates and prints a one-line summary: "No candidates surfaced — no eligible input signal found." Exit cleanly; do not create `reflect_declined.md`.
- **Reflect run with N > 0 raw candidates but zero survive the anti-redundancy filter.** Print a one-line summary: "N candidates generated, all filtered as redundant against {canonical | archive | declined | excluded}." Show no interactive loop; exit cleanly.
- **Staleness nudge fired when `reflect` not yet defined.** Impossible by construction in v1.2 (reflect ships in the same release), but if `last_reflect_at` is unset on first `init` or `doctor` run after upgrade, the hint MUST NOT fire — treat unset as "fresh," not "stale."
- **Supersede collision on a memory the user just declined.** If a candidate would supersede an existing entry AND matches an entry in `reflect_declined.md`, the decline ledger takes precedence: the candidate is dropped by the anti-redundancy filter before the supersede check runs. The user is not asked twice.
- **Cross-harness scope (Cursor or generic harness with Sources 3+4+5).** All R1–R11 behavior holds. The `--from-session` and `--since-last-reflect` flags either error with a clear message ("transcript ingestion is Claude-Code-only") or are absent from the harness-specific README — architect chooses during the ADD.
- **`--from <path>` points to a non-existent or unreadable path.** `reflect` errors with a clear message identifying the path and exits without writing to `reflect_declined.md` or the canonical store.
- **`--since-last-reflect` invoked when `last_reflect_at` is unset.** Treat as "no prior reflect" — fall back to a bounded default window chosen by the architect (e.g., last 30 days) and print an explanatory line, OR error with a clear message — architect chooses during the ADD.
- **User accepts a `save` flagged as `would-supersede`.** Routing enters the v1.1 supersede flow; the existing entry is archived per v1.1 supersede semantics; no special v1.2 handling required beyond surfacing the flag.
- **User issues `done` with N candidates unactioned.** Unactioned candidates are recorded in the run log but NOT written to `reflect_declined.md`. They may re-surface on a subsequent run (declining is an explicit user action, not the absence of one).
- **User issues `edit <id>` then aborts the edit.** No state change; the candidate remains in the report and may be saved, declined, or edited on a subsequent loop iteration.
