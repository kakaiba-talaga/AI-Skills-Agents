**Critical-1 — The ADD's `~/.claude/projects/<active-slug>/sessions/<id>.jsonl` path is wrong on Claude Code as installed today.**

- **Documents and sections:** ADD §7 ("Source 1 — Claude Code `.jsonl` session transcripts") and plan `M3.implement.5` task description plus its acceptance criterion (1). Scoping doc §1.4 inherits the same path.

- **Quote (plan M3.implement.5 description):** "`--from-session <id>` reads exactly one session at `~/.claude/projects/<active-slug>/sessions/<id>.jsonl`."
- **Quote (plan M3.implement.5 acceptance criterion 1):** "Two flag shapes documented with their paths."
- **Direct codebase evidence:** `ls ~/.claude/projects/D--Repositories-Personal-Git-AI-Skills-Agents/` returns `.jsonl` files at the **top level** of the project directory (e.g., `14e0a463-5e3b-4313-a5c6-b4fa311e6a25.jsonl`); `ls ~/.claude/projects/D--Repositories-Personal-Git-AI-Skills-Agents/sessions/` returns "No such file or directory." The `sessions/` subdirectory does not exist on this machine. The actual path is `~/.claude/projects/<active-slug>/<id>.jsonl`.
- **Issue:** This is the load-bearing path the structural pre-check is supposed to validate. If M3.implement.5 documents the wrong path, the pre-check will fail on every Claude Code transcript on this machine — and the ADD's stated mitigation ("graceful fallback to Sources 3+4+5 with a structured warning") will mask the bug under a generic warning rather than surface it to the user. The ADD even hedges the path with "(or wherever Claude Code stores transcripts — see Risk below)," which suggests the architect was uncertain at write time but did not verify against an actual install.
- **Confidence:** HIGH. Verified by direct directory listing in the active project.
- **Impact:** Source 1 (`--from-session` and `--since-last-reflect`) is unusable as written on this Claude Code install. Every transcript ingestion attempt routes to the fallback path; the user loses the Claude-Code-only opt-in feature without an obvious cause. This is a "v1.2 ships broken on the architect's primary harness" failure mode. M3.implement.5 documents an empirically wrong path; M3.implement.5 acceptance closes against the documented path; M5.verify.1 walks the Cursor case where the flag errors at parse time, so it never exercises the actual transcript path; M7.verify.1's Step 1 marks `--from-session <id>` as "Optional" so it can pass without ever touching the broken path.

Propagate the correction to scoping doc §1.4 and plan M3.implement.5. If Claude Code's actual storage path differs across versions (which the existing `.jsonl` format-fragility risk already names), document the discovered path as the v1.2 baseline and let the same structural pre-check the ADD already designs handle future drift. Routing owner: **project-scoper** (single doc edit; architect re-dispatch only needed if the architect treats the path as a binding design choice rather than a typo against the actual install).

### Major

**Major-1 — Reference Set D consumption shape is unresolvably ambiguous between filter-applied and LLM-prompt-applied (Gap G1).**

- **Documents and sections:** ADD §1 ("Out of scope") line ~96; scoping doc §6 Gap G1; plan M3.implement.9 acceptance criterion (8); requirements §R5 ("Reference Set D — 'What NOT to save' categorical exclusion rule").
- **Quote (ADD §1):** "v1.2 reads the section by heading match (`## What NOT to save in memory`) and treats the body as a **free-text rule corpus the agent prompts itself with**. No structured parsing."
- **Quote (requirements §R5):** "After candidate generation and before the report, `distill` applies a deterministic filter that drops any candidate whose **slug-overlap + tag-overlap + body-token Jaccard** score exceeds a configurable threshold against any of the four reference sets below. ... **Reference Set D — 'What NOT to save' categorical exclusion rule.** A stable readable codified rule (see R10)."
- **Quote (plan M3.implement.9 description):** "The four reference sets are: canonical store filtered to relevant tiers; archive at ~/.cross-memory/archive/; per-project reflect_declined.md; ~/.claude/CLAUDE.md What NOT to save section."
- **Quote (plan M3.implement.9 acceptance criterion 8):** "Reference Set D read is best-effort — if ~/.claude/CLAUDE.md is missing or unreadable, a structured warning logs and the filter proceeds with empty Reference Set D."
- **Issue:** The requirements doc and the plan both list Reference Set D as a fourth signal-source for the disjunctive slug/tag/body-Jaccard filter. The ADD describes Reference Set D as a free-text rule corpus the agent uses to prompt itself during raw candidate generation. A free-text rule corpus produces no slug, no tag set, and no body to Jaccard-compare against — the three filter signals are mathematically undefined when one side is unstructured prose. Either (a) the filter applies Reference Set D differently from Sets A/B/C (likely by category-match against the LLM-extracted exclusion categories), or (b) Reference Set D is not filter-applied at all and the architect's framing in the ADD is correct but the requirements' "four reference sets" wording is a category error. The scoping doc names this in Gap G1 and proposes Option (b) as the simpler resolution. This review confirms G1 as a Major finding: a competent executor reading the plan as written will hit the ambiguity within the first hour of M3.implement.9 — when they try to write the disjunctive filter against four signals and discover one of the four has no comparable shape — and stop to ask. There is no way to write M3.implement.9's section without picking a path; picking the wrong path forces a follow-up dispatch.
- **Confidence:** HIGH. The mathematical incompatibility is verifiable by inspection; the requirements / ADD framings cannot both be literally true.
- **Impact:** Blocks M3.implement.9 within the first hour as predicted. If unresolved, the executor either invents a per-set filter shape (Option a) and bakes it into SKILL.md, or implements three structured sets plus one prompt-applied corpus (Option b) and re-words SC5's "four reference sets" framing. Both produce a v1.2 that ships, but the first verifier walk against AC15 (determinism) will surface the disagreement: Option (a) produces a filter that varies with the rule's exact wording, weakening reproducibility across machines that may have different `~/.claude/CLAUDE.md` content; Option (b) produces a stable filter but the SC-5 traceability in v1.2-shipped.md will read awkwardly.
- **Recommendation:** **Project-scoper resolves G1 in the scoping doc** before executor pickup by picking Option (a) or Option (b) on architect input and updating scoping doc §6 G1's resolution row from "Recommended Resolution" to "Resolution: <chosen path>." Recommended path: Option (b) — Reference Set D is LLM-prompt-applied only, and SC5 / R5 / plan M3.implement.9 reword "four reference sets" to "three deterministic reference sets (A/B/C) plus one LLM-prompt-applied exclusion corpus (D)." This matches the ADD's free-text framing without forcing the rule into a structured shape. The scoping doc, the M3.implement.9 acceptance, and the v1.2-shipped.md template all change one line each; no estimate change beyond the +0.25h already booked under G1's recommendation.

**Major-2 — Filter test fixtures are missing from M1 and M3; M3.verify.5's AC15 determinism walk cannot be reproduced as written (Gap G2).**

- **Documents and sections:** Scoping doc §6 Gap G2; plan M3.verify.2 / M3.verify.3 / M3.verify.5; ADD §10 (edge case "N > 0 raw candidates, zero survive the filter").
- **Quote (plan M3.verify.5):** "Run /cross-memory reflect twice in a row on a frozen source set. Confirm both runs produce identical candidate lists in identical order."
- **Quote (plan M3.verify.5 acceptance criterion 1):** "Two consecutive runs on identical inputs produce byte-identical candidate sets in identical order."
- **Quote (scoping doc Gap G2):** "M3.verify.5 asserts AC15 (filter determinism) by running reflect twice on a 'frozen source set' — but the plan does not specify what 'frozen' means or where the fixture lives. Two consecutive runs on a live repo are not deterministic if the verifier is also writing to `state.toml` or `reflect_declined.md` between them."
- **Issue:** AC15 closure requires byte-identical candidate sets across two consecutive runs on the same source. The plan does not define what a "frozen source set" is. On a live repo: Source 3 (`git log`) can change between the two runs (if a commit lands in between); Source 4 (glob over `docs/plan/**`) can change (if a file is added); state writes between runs (`state.toml`'s `last_reflect_at` field) can alter the staleness-check side effects; the verifier may also be writing scratch under `_tmp_M3_verify_5/` between runs (cleanup happens at task end, not between runs). Without a controlled fixture, the verifier's pass/fail signal is not reproducible across runs or machines. The same critique applies to M3.verify.2 (decline ledger creation) and M3.verify.3 (project-goal exclusion) — both need controlled inputs that the plan does not define.
- **Confidence:** HIGH.
- **Impact:** AC15 closure may pass on the executor's machine and fail on the verifier's. Or the same machine runs the verifier twice and gets different verdicts because a git commit happened. The verdict is unreliable; the deterministic filter's guarantee is unobservable in the verifier walk as written. The scoper has correctly sized the fix at +0.75h.
- **Recommendation:** **Project-scoper adds a new task to M1 (not M3).** Add `M1.implement.4 — Define filter test fixtures` at 0.75h: a `docs/cross-memory/v1.2-test-fixtures/` directory (or under `skills/cross-memory/test-fixtures/` if the manifest deploy makes that preferable) with a frozen git-history snapshot (raw commit log captured as a Markdown file), a frozen `docs/plan/**` source slice, a frozen handoff slice, a frozen `reflect_declined.md` precursor, and a frozen canonical-store fixture. M3.verify.2/.3/.5 then read from the fixture directory rather than the live repo. Booking the task under M1 keeps the substrate cleanly separated from the executor stage; M3 then depends on M1.verify.1 → M1.implement.4 as a precondition. **Estimate impact: 31.25h + 0.75h = 32.0h total, confidence band ±6h holds.** Routing: **project-scoper** (adds the task; planner updates the dependency table; no architect involvement needed — the fixture shape is a verifier-stage choice).
