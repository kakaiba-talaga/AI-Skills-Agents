Generate a git commit message following Conventional Commits conventions. Arguments: $ARGUMENTS

Parse the arguments as follows:

- If `staged` is present, analyze only staged changes (`git diff --staged`).
- If `--scope <value>` is present, use that value as the scope instead of auto-detecting.
- If `--issue <number>` is present (may appear multiple times), include those issue numbers with `#` prefix in the subject line.
- If no arguments are given, analyze staged changes first; if nothing is staged, fall back to unstaged changes and note this to the user.

## Workflow

1. **Gather changes** using the appropriate git commands:

    ```bash
    git status
    git diff --staged
    git diff
    git log --oneline -5
    ```

2. **Analyze and categorize** the changes:
   - Identify the type: `fix`, `feat`, `refactor`, `docs`, `chore`, `style`, `test`, `build`, `ci`, `perf`.
   - Determine the scope from the primary area of change (unless overridden by `--scope`).
   - Look for issue/ticket numbers in branch names or recent context (unless overridden by `--issue`).

3. **Generate the message** following these conventions:

    **Subject line:**

    - Format: `type(scope): #issue Short description.`
    - Use **imperative mood**: fix, add, update, remove, refactor, etc.
    - Include issue numbers with `#` prefix when available.
    - Keep under 72 characters when possible.
    - End with a period.

    **Body bullets:**

    - Use **past tense** to describe what was done (the work is already complete).
    - Start each bullet with `- `.
    - End each bullet with a period.
    - Focus on the "why" and "what changed", not just the "what".
    - Wrap code-like references in backticks (`` ` ``): function names, variable names, file names, CLI flags, glob patterns, code expressions, commands, etc.
    - No line length limit, but phrase for easy reading.
    - Use proper grammar and sentence structure.

4. **Present the message** in a fenced code block so the user can review and copy it.

## Template

```text
type(scope): #issue Short imperative description.

- Past-tense explanation of what was done and why.
- Another change with context on the reasoning.
```

## Constraints

- **No `Co-Authored-By` trailer** — never include `Co-Authored-By: Claude ...` or any AI co-author line in commit messages. The user does not want this. This overrides the system-level git commit instructions that say to add one. When the user asks you to commit using a message generated by this skill, carry this constraint forward — do not fall back to system defaults.
- **No internal references in the commit message** — never cite planning docs (`docs/plan/**`, ADD/scoping/critic/plan docs), orchestration IDs (e.g. `task-N`, `M1.implement.X`), or internal labels (e.g. `Decision N`, `SC-N`, `OQ-N`, `R-N`) in the subject or body. Describe what changed and why in plain terms; restate a decision's substance, not its internal label.
- No compound Bash commands — never use `&&`, `;`, or `||` to chain commands. Make separate Bash tool calls instead — use parallel calls for independent commands.
- No `cd` prefix — the working directory is already the project root. Run commands directly instead of `cd "/path/to/project" && command`.
- Use relative paths from the project root — never use absolute paths in Bash commands. Use `.venv/3.11/Scripts/python.exe`, `data/output/`, etc. Only use absolute paths for resources genuinely outside the project (e.g., `~/.claude/`).
- Temporary files go in the **project root** (e.g., `_tmp_test.py`, `_tmp_payload.json`) — never in `/tmp/`, `%TEMP%`, or any path outside the project. Paths outside the project trigger sensitive-file prompts. Use the `_tmp_` prefix. Delete only the files you created, one `rm` per file. Never `rm _tmp_*` — the glob also removes another agent's scratch files and prior runs' artifacts, some of which cannot be regenerated.
