# Foreground/Background Dispatch Policy

## Background (default)

Default is **background** (`run_in_background: true`) — the team manager dispatches and keeps its turn instead of blocking, so the session stays conversable for the life of the dispatch. Every agent spawn is background unless the task matches one of the closed foreground exceptions.

Keeping the session conversable is a first-class reason to background a dispatch, independent of orchestrator throughput. A solo long-running task is precisely the case where the user most needs to be able to interject — so "it is the only ready task" is never a reason to choose foreground.

## Foreground (closed list)

This is the closed list referenced above. When a dispatch matches none of the following, it runs in the background — the exceptions are enumerated, not left to judgment.

- **F1 — Nested `Skill` invocations** (the cleanup skill, the memory skill, the persistence-loop skill). No background mode exists for the `Skill` tool at all — the next assistant turn *is* the skill's processing. This is a harness incapability, not a choice (see `SKILL.md`'s Non-negotiables section, item 10's Skill-tool two-turn caveat).
- **F2 — The three advisory preflights** (`code-intel`, `corpus-search`, `docs-lookup`). Each phase's contract requires the result before the downstream brief is composed — it also protects the self-contained-brief rule, since a brief cannot cite a result that has not arrived (see `phase-preflights.md`'s Phase 2.5b and Phase 2.5c Trigger predicate sections, and its Phase 2.5d Dispatch trigger point section).
- **F3 — The Phase 2.5 `preflight` dispatch.** A critical-check failure must stop the run before the first dispatch; a detached preflight would let dispatches start against an unready environment (see `phase-dispatch.md`'s Phase 2.5 — Preflight Validation section).
- **F4 — `work-verifier`, whenever its verdict is consumed in the same turn.** The `status` route renders and stops in one turn (`phase-intake.md`'s input-routing table, `status` row); `resume` must classify orphans before it can decide what to dispatch (`phase-intake.md`'s input-routing table, `resume` row); the health-action branch selects its action from the verdict in the same beat (`phase-dispatch.md`'s Phase 3 — Dispatch Loop section, health-action sub-step); and the beat-level dispatch fires whenever a task classifies as unknown, not only when a sustained overrun fires.
- **F5 — `change-analyzer`, when its verdict selects the same turn's branch.** Covers security-surface routing (`SKILL.md`'s Edge Cases section, Trivial/mechanical changes bullet), the per-stage conditional skip (`SKILL.md`'s Edge Cases section, Per-stage conditional skip bullet), and low-confidence-trivial promotion (`phase-intake.md`'s Trivial Dispatch section, Promotion check step). The verdict *is* the branch condition.
- **F6 — Branch-creating `git-master`**, both the Phase 1.5 dispatch (`phase-intake.md`'s Phase 1.5 — Branch Isolation section) and the deferred-on-promotion one (`phase-intake.md`'s Trivial Dispatch section, Promotion check step, Branch isolation sub-step). The working branch is a precondition for every code-modifying dispatch, and a mis-sequenced detached spawn lands executor work on the base branch. The block is bounded — git-master's timeout budget is five minutes (`work-verifier.md`'s Orphan detection section, agent-type timeout table).
- **F7 — `rollback`, on every scope level.** The `broken` verdict path is a strict sequence: revert, then re-dispatch on a clean slate. It is a same-task recovery inside the dispatch loop's result-processing step with no board task behind it, so no dependency edge exists to carry the order (`phase-dispatch.md`'s Phase 3 — Dispatch Loop section, health-action sub-step, `broken` outcome bullet; `work-verifier.md`'s Handoff section, `broken` verdict row). The block is bounded — rollback's timeout budget is five minutes (`work-verifier.md`'s Orphan detection section, agent-type timeout table).

  Foreground alone is insufficient here, so F7 also carries a precondition:

  > Before a `rollback` dispatch starts, zero other tasks are `in_progress`, or the rollback's declared scope is verified file-disjoint from every in-flight sibling.

  Blocking stops *new* work from starting, but siblings dispatched before the `broken` verdict arrived are still running. At full-run scope the rollback agent runs a stash push with no pathspec — a whole-tree operation (`rollback.md`'s Rollback procedure section, Step 5 — Stash first, full-run case). The rollback agent's own overlap check compares against files modified by *successful* tasks, not in-flight ones, so it does not cover this case (`rollback.md`'s Rollback procedure section, Step 3 — Check file overlap). `SKILL.md` already forbids parallel git operations on the same branch, and a whole-tree stash is the extreme instance of that (`SKILL.md`'s Parallel Safety Rules section, Never parallelize list, Git operations on the same branch bullet).
- **F8 — The Phase 4 completion-menu `git-master`, all three acting options.** Each option consumes the result in the immediately following procedure step: confirming the merge landed (`completion-options.md`'s Option 1 — Merge locally section, step 3), running `gh pr create` once the push completes (`completion-options.md`'s Option 2 — Push and open PR section, step 2), and confirming the branch deletion (`completion-options.md`'s Option 4 — Discard section, step 3). A detached push means the pull-request command would run against a ref that is not yet on the remote.
- **F9 — The two Phase 4 internal dispatches.** One dispatches an agent to create a missing deliverable, with the step reading "before proceeding" (`phase-completion.md`'s Phase 4 — Completion section, step 2); the other dispatches a verifier for the final pass (`phase-completion.md`'s Phase 4 — Completion section, step 3). The first blocks because step 3 follows it immediately with no check between them, so a still-running deliverable dispatch would leave the verifier to run its final pass against an incomplete deliverable set and report a pass that isn't earned yet. The second blocks because it is the last correctness check before completion is reported, and detaching it would only make the wait implicit rather than explicit. Re-entrant zero-in-progress guards sit immediately before step 4, again immediately before step 9, and a third time immediately before step 9b; it is this last guard that guards the step that deletes the run's state file and handoff directory (`phase-completion.md`'s Phase 4 — Completion section, step 9b delete list), since the pre-step-9 guard explicitly disclaims that role and points forward to it. The completion menu can still reach a forced worktree removal (`completion-options.md`'s Worktree cleanup by provenance check section, step 3c).
- **F10 — The deslop re-verification `verifier`.** Its verdict selects a destructive branch in the same turn — on failure, the savepoint is restored by popping a stash or checking out the savepoint commit (`integrations.md`'s Deslop Integration section, How it works step 5). A delayed restore would discard work that landed after the verdict was formed.
- **F11. The relocation dispatch inside a pre-delete durable-content sweep.** Any dispatch or nested-skill invocation that a durable-content sweep makes to move content to its real home, for instance a documentor dispatch for a non-obvious decision, runs in the foreground and must return before that sweep's own delete step begins. Two sites run this sweep and both are covered: 9a's relocation sweep before 9b's delete on the full pipeline (`phase-completion.md`'s Phase 4 completion section, step 9a), and the trivial path's On-result cleanup sweep before its own board delete (`phase-intake.md`'s Trivial Dispatch section, On result step), which imports the identical destination table and documentor-dispatch branch from 9a. Same-turn consumption forces it at both sites: the relocating agent may be reading the very board or handoff files the sweep's own delete step is about to remove, so a detached dispatch could have its own source material deleted out from under it mid-run.

## Extending the foreground list

The list above is closed, and its value depends entirely on staying that way. Any addition must name one of exactly two justifications: **the same-turn consumption that forces it** — the orchestrator needs the dispatched agent's result within the same turn it spawned it, so it cannot proceed without blocking — or **a harness incapability** — the harness offers no way to run that dispatch detached. Nothing else qualifies.

Two reasons are explicitly inadmissible, because they are the two that will actually be offered. "Nothing else is ready" is never a reason to block — conversability is a first-class reason to background a dispatch regardless of throughput, already argued in this file's Background (default) section. "It feels safer" is not a justification — if blocking is genuinely required, one of the two admissible reasons above will be nameable; if neither is, the unease is not evidence.

The list was derived by mechanically sweeping every dispatch site under this skill's directory and classifying each by whether its result is consumed in the same turn — not by recalling which agent types seem risky. Agent type is the wrong unit of enumeration; the dispatch site is the right one. The git operation that creates the working branch and the git operation dispatched from the completion menu both sit on this list, while that same agent type is an ordinary background dispatch everywhere else; the verifier that runs the Phase 4 final pass and the verifier that re-checks after a deslop restore both sit on this list, while that same agent type is an ordinary background dispatch everywhere else. Enumerating from recall would either miss a site like these or wrongly blanket-list the whole agent type — two thorough review passes each missed one, and nothing found the full set until a mechanical sweep ran. Any future addition must name its site the same way: trace the actual dispatch call, don't recall the agent type's reputation.

## User override

A user can ask for any specific dispatch to run in the foreground ("wait for this", "block until it finishes", "run this in the foreground"), and the orchestrator honors it for that one dispatch. This is not an exception to the closed list above and not a member of it: the user is setting the dispatch mode for a single dispatch, a choice that needs no justification from either of the two admissible reasons. Honoring it therefore sets no precedent for the list either, since the admission rule governs what can be added to the list, and a one-off instruction that never joins the list cannot loosen it.

## Estimates are still required

Every task still needs an `estimated_minutes` value before dispatch, even though the closed list above is now the only input to the foreground/background decision — the estimate is not for mode selection. Two other systems consume it: the health-monitoring thresholds that flag `⚠️ SLOW` and `🔴 OVERRUN` against a multiple of the estimate (`phase-dispatch.md`'s Phase 3 — Dispatch Loop section, Step 4 — Process results step), and the orphan-suspicion timeout, computed as the smaller of the agent-type default and three times the task estimate (`work-verifier.md`'s Orphan detection section). When a task has no estimate, produce a rough one before dispatching — from project history or task complexity signals.

## Parallel Batch Decisions

A parallel batch dispatches as a single background unit — mode follows closed-list membership plus any user override already in effect for a member, so the orchestrator makes no independent per-task foreground/background judgment inside a batch. Every spawn in the batch still rides the batch's single message, per `phase-dispatch.md`'s Phase 3 — Dispatch Loop section, Step 3 — Dispatch agents step.

When a batch contains a dispatch that matches the closed list above or is covered by this file's User override section, that dispatch runs first and alone, and the rest of the batch dispatches afterward — a mixed batch serializes the blocking member rather than mixing a closed-list spawn with background siblings in one message. When more than one member of a batch is blocking, they serialize one at a time in board order, and the remaining background members dispatch only afterward.

Serialization is a mixed-batch rule only. When every member of a batch is on the closed list, read-only, and file-disjoint from its siblings, the batch rides one message concurrently like any other batch. The case this covers: `/ops resume` dispatches one `work-verifier` per remaining in-progress task (`phase-intake.md`'s input-routing table, `resume` row), and every `work-verifier` dispatch is read-only (`work-verifier.md`'s Brief Format section, File-class allowlist line) — nothing forces those siblings apart.

Background dispatch also lets a second batch form before an earlier one finishes, unlike the blocking default. What the concurrency cap and file-disjointness check must do about tasks already in flight is defined in `phase-dispatch.md`, alongside its Phase 3 — Dispatch Loop section, Step 2 — Batch parallel work step — not restated here.

## Hard predecessors

When two dispatches genuinely must happen in a fixed order, that requirement is a dependency edge (`blocked_by`) on the task board — never a choice to run one of them in the foreground so it blocks the other. Foregrounding a dispatch happens to force sequencing, but it is a workaround: it encodes an ordering requirement in a mechanism designed for something else, and nothing on the board records that ordering was the reason. A `blocked_by` edge, by contrast, survives a resume and is visible to anyone reading the board. Dispatch mode is not an ordering mechanism and must not be used as one.

The sharpest case is the branch-creating `git-master` dispatch (F6 in the closed list above): the working branch is a precondition for every code-modifying dispatch, and a spawn issued before the branch exists lands its work on the base branch. It would be easy to read F6 as this section's exception, as though blocking were an acceptable way to enforce that precondition. It isn't, and that reading gets the relationship backwards. F6 blocks because it is one of the dispatches that runs before the task board exists, so no `blocked_by` edge is available to it at all; the next section explains why. Where an edge is available, use it — F6 is foreground only because it falls outside that "where."

## Ordering before the board exists

Six dispatch kinds run before the task board exists: requirement clarification, architecture, and planning (`phase-intake.md`'s Phase 1 — Intake and task board section), scoping and plan critique (`phase-intake.md`'s Phase 1a — Plan Validation section), and the branch-creating git operation (`phase-intake.md`'s Phase 1.5 — Branch Isolation section). The board itself is created afterward, in `phase-intake.md`'s Phase 2 — Task Board Creation section, at its state-file initialization step — so none of these six dispatches has a `blocked_by` edge available; there is no state file yet for one to reference. What orders them instead is the phase contract itself: the intake procedure states the sequence for each, and following that procedure is the ordering mechanism. A pre-board chain is therefore never batched, since a batch rides one message with no ordering between its members. The sharpest case is the Tier 3 pair in `phase-intake.md`'s Phase 1a — Plan Validation section: `project-scoper` dispatches, then `critic` reviews the combined plan and scoping doc — riding that pair in one batch would have the critic reviewing scoper output that does not exist yet.

## Interaction with Health Monitoring

Background agents are subject to health monitoring by the team manager — now nearly every dispatch, where before it was the rare one, since a blocking dispatch could not be monitored mid-flight. The team manager checks background agent health at every check-in event: after foreground agents return, after background completion notifications, and on the turn that responds to a user message — the check-in still happens, it just no longer gates the reply. Emit `⚠️ SLOW` when elapsed exceeds 1.5× estimate and `🔴 OVERRUN` when elapsed exceeds 2.5× estimate. A sustained `OVERRUN` may also trigger the health-action sub-step, whose re-dispatch leg is gated on a liveness determination — a task counts as abandoned only once the orchestrator no longer holds its spawn (`phase-dispatch.md`'s Phase 3 — Dispatch Loop section, health-action sub-step).

## When a user message arrives mid-run

A user message can arrive at any point while a dispatch is in flight — that possibility is the entire reason background is the default rather than an optimization on top of it. When one does, the team manager follows this six-step procedure:

1. **Answer first.** Respond to the user's message before any bookkeeping. Never defer the answer to wait for an in-flight agent.
2. **Run the beat in the same turn, after the answer.** Evaluate the slow and overrun thresholds (`phase-dispatch.md`'s Phase 3 — Dispatch Loop section, Step 4 — Process results step); evaluate the sustained-overrun trigger (`phase-dispatch.md`'s Phase 3 — Dispatch Loop section, health-action sub-step); evaluate any armed confirmation deadline (`phase-dispatch.md`'s fable-escalation autonomous timeout mechanism). If the beat fires a diagnostic dispatch, spawn it in this same turn — the user has already been answered, so the diagnosis costs them nothing. The beat mutates no state-file field, so it is not a status change, and the Cursor write-then-verify-then-display ritual (`phase-dispatch.md`'s Cursor state file sync section, Required ritual) does not fire on it.
3. **Render board state proportionally.** The dashboard-gating non-negotiable governs: three or more non-internal tasks gets the full dashboard, two or fewer gets a one-liner (`SKILL.md`'s Non-negotiables section, item 8). Render the *full* dashboard only when the user asked for status, when the beat produced a health warning, or when the answer changed the plan. Otherwise emit one in-flight line carrying elapsed time and health indicator. A question about model choice should not be answered with a dashboard.
4. **Apply any mid-run command the message carries** — stop, pause, status, skip, drop, do-next, add, reprioritize (`SKILL.md`'s Interruption Handling section, summary-of-user-commands table, and `interruption-recovery.md`'s Reprioritize, Inject Tasks, and Remove Tasks sections for the detailed procedures) — including the cache invalidation that a mid-run command triggers (`phase-dispatch.md`'s Phase 3 — Dispatch Loop section, Step 1 state-cache invalidation list).
5. **Do not spawn new work while answering** unless the message itself unblocks a dispatch, for example by answering a clarification request (`phase-dispatch.md`'s NEEDS_CLARIFICATION handling). This keeps the answer turn cheap and keeps the status-spawn atomicity non-negotiable unambiguous — any in-progress write in that turn must still ride its own spawn.
6. **Continue.** The answer turn is a mid-loop event, never terminal — the same posture the contract takes for a nested-skill return (`SKILL.md`'s Non-negotiables section, item 10). No closing phrase. The loop resumes at the next beat. **A beat is guaranteed while at least one task is in progress** — not unconditionally: the documented case is a confirmation deadline that is armed and evaluated only at the next beat with no wall-clock interrupt, where the task whose escalation armed it is not itself in flight (`phase-dispatch.md`'s fable-escalation autonomous timeout mechanism). Where a deadline is armed and nothing is in flight, the fallback named in the dispatch companion applies.

## When a background dispatch leaves nothing else ready

The standard pipeline is linear — implementation, then verification, then review, then documentation, each stage waiting on the one before (`SKILL.md`'s Handoff Chains section) — so on a chain like that, almost every background spawn is the only task ready to start, and the team manager gets its turn back with nothing further to dispatch and no result yet to process. That turn still has content: the team manager emits the dispatch line, ends the turn, and treats the agent's arriving completion notification as the next beat. Ending the turn here is not a run completion — the heavier notion of completion that requires real deliverables on disk before it can be reported (`SKILL.md`'s Non-negotiables section, item 4) does not apply, because this turn is not claiming anything is finished; it is a pause in an ongoing loop, not the loop's end. No closing phrase is emitted, for the same reason none is emitted on a nested-skill return (`SKILL.md`'s Non-negotiables section, item 10) — a closing phrase would tell the user the run is over while an agent is still working.

## Harness conditions

This skill runs on two harnesses, Claude Code and Cursor, and background dispatch has been confirmed to work on both.

On Claude Code, the agent-spawning tool accepts a background parameter, and the harness's own documentation states that subagents run in the background by default, with the parameter passed explicitly only when a synchronous run is wanted. This has also been observed directly: a dispatch ran detached while the team manager kept its turn, and a completion notification arrived once the agent finished.

On Cursor, the task-spawning tool was probed live in three stages — the parameter name, whether the session stays conversable while a task runs, and the resulting skill-level behavior — and all three checked out against the live tool.

Because Claude Code already defaults to background, it would be tempting to let that default carry the decision there and pass the parameter only on Cursor. Don't. **The flag is passed explicitly in both directions** — explicitly for background dispatches and explicitly for foreground ones — never relying on either harness's default to produce the outcome this policy requires. A harness default sits outside this contract and can change without notice; a dispatch that silently inherits one is correct only for as long as the default happens to agree with the policy, and nothing would signal the day it stopped agreeing. Naming the flag on every dispatch keeps that dispatch self-describing no matter what the harness defaults to.

On Cursor, this rule applies verbatim — no adaptation, no separate procedure.

## Interaction with Worktree Isolation

`run_in_background` and `isolation: "worktree"` are orthogonal (independent; can be combined). `run_in_background` controls whether the team manager blocks while waiting; `isolation: "worktree"` controls whether the agent gets its own copy of the repo. A long-running executor task that also needs file isolation can use both. When combining, the team manager must track both the background notification and the worktree branch for later merge.
